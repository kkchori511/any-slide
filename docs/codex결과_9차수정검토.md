# 9차 수정 검토 결과 (v1.11.0)

## 요약

- `main`(`23053f6`)과 `table-resize`(`8fac3b6`, 검토 시 HEAD)의 차이를 코드 읽기와 Node 격리 실행으로 검토했다.

## 문제 목록

### 1. [높음] 앱 조작으로 51개 비율을 저장하면 같은 앱의 검증기가 다시 열지 못함

- **위치:** `app/app.js:1048–1056`, `:1060–1062`, `:1117–1123`; 제한 검사 `app/deck-spec.js:508–513`
- **증상:** 비율이 있는 50행 표에서 [줄 +]를 누르면 `rowH`가 51개가 된다. 앱은 저장하지만 `sanitize`는 이를 거부한다. 저장 JSON의 [불러오기]·패키징이 실패하고, 브라우저 재시작 때 저장본이 깨진 덱으로 처리될 수 있다. 열 추가 및 50칸을 넘는 표에서 처음 경계선을 끄는 경로도 같은 제한 불일치가 있다.
- **근거 [실행 확인 — 격리]:** 실제 `tableOp`·`setTracks`를 VM에서 실행했다. 50행·`rowH` 50개 덱에 `tableOp('addRow')`를 실행하자 배열이 51개가 됐고, 결과 덱을 실제 `sanitize`에 전달하면 예외가 발생했다.
- **근거 [정적 확인]:** `tableOp`, `setTracks`, 끌기의 비율 생성에는 배열 길이 제한이 없으며 저장 전에 재검증하지 않는다. 반면 `sanitize`는 50개 초과에 예외를 던진다. 기존 표 내용 자체에는 같은 50행·50열 제한이 없으므로, 오래된 큰 표에서도 문제가 생길 수 있다.
- **수정 제안:** 앱과 검증기의 한도를 공통으로 적용한다. 배열 한도를 유지한다면 한도에 도달한 추가·크기 조절을 변경 전에 막고 알리거나, 더 큰 표도 지원할 정책으로 함께 바꾼다. 비율 배열만 조용히 잘라 내면 내용과 정렬이 달라지므로 피한다.
- **확인 방법:** 49→50→51행/열, 비율 없음/있음, 기존 51행/열 표의 첫 끌기를 시험한다. 앱에서 성공한 모든 조작 결과는 `sanitize` 왕복과 [저장]→[불러오기]를 통과해야 한다.

### 2. [중간] 비율의 정규화 기준과 개별 clamp가 달라 다른 행·열도 바뀜

- **위치:** `app/app.js:1048–1054`, `:1060–1062`, `:1114–1125`; `app/deck-spec.js:374–379`
- **증상:** 열 경계 양옆만 조절하려 해도 다른 열까지 바뀔 수 있다. 열을 추가하는 등 행 높이와 무관한 작업이 기존 행 비율을 바꾸기도 한다. 이는 소수 둘째 자리 반올림 오차보다 큰 변화다.
- **근거 [실행 확인 — 격리, 행]:** 정상 검증된 `rowH:[0.2,20]`은 렌더링용 `tableTracks`에서 `[1,100]`이다. 여기에 `tableOp('addCol')`만 실행하자 `setTracks`가 각 값을 20 이하로 잘라 `rowH:[1,20]`으로 저장했다. 기존 100:1이 20:1로 바뀌었다.
- **근거 [실행 확인 — 격리, 열]:** 실제 `startTableResize`와 저장·CSS 생성 함수를 사용하고 칸 너비만 DOM 대역으로 제공했다. 너비 `[800,60,740]`의 두 번째 경계를 10px 옮기자 저장 비율이 `[1.5,0.2,1.37]`이 됐다. 이 비율을 같은 1600px 폭으로 환산하면 손대지 않은 첫 열도 800px에서 약 781.76px로 바뀐다. 실제 브라우저의 소수점 배치는 측정하지 않았지만 저장된 비율 자체의 변화는 확인했다.
- **원인:** 행은 최솟값 1 기준, 열 끌기는 평균 1 기준으로 값을 만든 뒤 모든 원소를 각각 `0.2~20`으로 자른다. 렌더링을 위한 값과 저장 가능한 값의 표현 범위가 같지 않다.
- **수정 제안:** 개별 원소를 자르기 전에 배열 전체에 같은 배율을 적용해 비율을 보존하면서 저장 범위에 넣는다. 범위 안에 담을 수 없는 비율이면 조작량을 일관되게 제한하고 알린다. 열 조작 시 바꾸지 않은 `rowH`는 다시 정규화·저장하지 않는 편이 안전하다. 반올림도 같은 경계값 시험에 포함한다.
- **확인 방법:** 최솟값·최댓값 조합, 좁은 열을 가진 3열 이상 표, 행 비율이 큰 표의 열 추가/삭제를 시험한다. 대상 외 비율과 전체 열 폭이 유지돼야 한다.

### 3. [중간] `check-deck`의 표 높이 추정이 `rowH`를 무시함

- **위치:** `.claude/skills/slide-deck/scripts/check-deck.mjs:63–68`
- **증상:** 행을 큰 비율로 늘려 표의 필요 높이가 달라져도 검사 결과는 글 양대로 행을 쌓은 표와 같다. 따라서 `rowH` 때문에 생기는 넘침을 검사가 알려 주지 못한다.
- **근거 [정적 확인]:** `tableTracks(slide).cols`만 사용하고, 각 행의 글 높이를 더해 `need(k)`를 계산한다. `rowH`·`tableTracks(...).rows`는 높이 계산에 쓰이지 않는다.
- **근거 [실행 확인 — 격리]:** 같은 합성 표에 동일한 `colW`를 두고 `rowH` 없음과 `[1,20]`을 각각 원본 `check-deck.mjs`로 검사했다. 종료 코드와 출력이 완전히 같았다. 이 실행은 검사 누락을 확인한 것이며 실제 화면 넘침을 촬영한 것은 아니다.
- **수정 제안:** 행별 내용 필요 높이를 먼저 구하고, 비율이 있으면 렌더러의 행 배분 방식에 맞춰 전체 필요 높이를 추정한다. 자동 높이 `fr` 모델을 유지한다면 단순 합 대신 공통 fr 단위와 행 비율을 반영해야 한다. 계산 신뢰도가 낮으면 최소한 수동 행 높이 표는 현재 검사 범위 밖이라는 경고를 둔다.
- **확인 방법:** 같은 글에 `rowH`만 바꾼 표, 짧은 글의 과도한 큰 행, grow 1.3·최소 글자 크기에서도 넘치는 표를 검사와 후속 화면 확인으로 비교한다.

## 추가 우선 검증 사항: 자동 높이 `fr`와 행 끌기의 픽셀 목표

**위치:** `app/app.js:323–329`, `:1097–1125`, `:448–465`; `app/style.css:129–133`

**[정적 확인]** `.table`은 높이를 명시하지 않은 격자이고, 행 끌기는 목표 픽셀 높이 목록을 비율로만 바꿔 `grid-template-rows`에 넣는다. `data-h`는 글자 맞춤의 비교 기준이며 격자 자체의 CSS 높이를 고정하지 않는다. 행의 최솟값을 1fr로 맞추는 것은 비율 문제를 줄이지만 픽셀 높이의 기준값까지 저장하지는 않는다.

**[추정 — 실제 브라우저 미확인]** 자동 높이 fr의 단위를 행별 내용 필요 높이가 결정하는 경우, 선택한 행의 목표 높이가 그대로 실현되지 않고 다른 행의 높이가 바뀔 수 있다. 예를 들어 2행의 내용 필요 높이를 `[100,60]`, 현재 비율을 `[1,1]`로 보면 모델상 높이는 `[100,100]`이다. 첫 행을 150px로 늘리려 비율 `[1.5,1]`을 넣으면 공통 fr 단위가 `max(100/1.5,60/1)`이 되어 모델상 `[100,66.67]`이 된다. 선택한 행은 그대로이고 다른 행이 줄어드는 예다. 이 수치는 Node의 수학 모델 결과이며 브라우저 레이아웃 측정값이 아니다.

후속 브라우저 검증에서는 내용 높이가 서로 다르고 이미 균등 fr인 표를 사용해, 끄는 행뿐 아니라 모든 행의 실제 높이를 전후 비교해야 한다. `fitBox`는 놓을 때 글꼴을 기본값부터 다시 재며 grow·축소를 적용하므로, 끄는 중과 놓은 후도 따로 확인한다. 이 조건에서 문제가 확인되면 비율과 함께 높이 기준을 유지하거나 명시적 트랙 크기를 사용하는 등 모델을 보완해야 한다. 이번 검토에서는 Chrome을 실행할 수 없어 확정 결함 수에는 포함하지 않았다.

## 확인한 정상 동작과 한계

### 경계 판정·끌기 수명

- **[실행 확인 — 격리]** 실제 `tableEdgeAt`를 칸 rect 대역으로 실행했다. 내부 열·행 경계는 인식하고, 칸 중앙과 1행 1열 표의 바깥 경계는 인식하지 않았다. 발표 모드와 회전 transform이 있는 표는 제외됐다.
- 화면 6px 판정은 `getBoundingClientRect`에 적용하고, 이동량은 `scale`로 나눠 슬라이드 좌표로 계산한다. 배율 0.5에서 화면 50px 이동이 슬라이드 100px 이동으로 반영되는 것을 확인했다. 교차점에서는 코드 순서상 열 경계가 우선이다.
- **[실행 확인 — 격리]** 다른 pointerId의 이동·해제는 무시됐다. window blur와 `finishDrag()`는 리스너 4개를 제거하고 작업을 끝내며, 연결된 표의 `fitBox`와 저장을 호출했다. 실제 창·터치 캡처 동작은 시험하지 않았다.
- **[정적 확인]** `renderStage`는 기존 DOM을 지우기 전에 `finishDrag()`를 호출하고, 끌기는 시작한 slide 객체를 보관한다. 따라서 장 이동·다시 그리기와의 공통 종료 절차를 사용한다. 비율은 이동 때마다 해당 slide에 반영되므로 취소는 시작 상태 복원이 아니라 현재 크기 확정이다. 기존 개체 끌기 정책과 같다.
- 글자 편집보다 경계 판정을 먼저 하고 `releaseFocus()`를 호출한다. 행의 내용 최소 높이는 해당 행의 모든 칸을 `align-self:start`로 재서 최댓값과 60px 중 큰 값으로 잡는다. DOM 대역에서 이 최소값 이하로 목표를 줄이지 않는 분기는 확인했다. 실제 글꼴·줄바꿈·그리드의 최소 높이까지 검증한 것은 아니다.
- 아주 좁은 표에서 양옆 열 합이 120px보다 작으면 60px씩 보장할 수 없다. 현재 clamp의 하한이 상한보다 커지는 경우를 따로 처리하지 않으므로, 지원할 최소 표 폭이나 해당 경계의 조작 금지 정책도 정하면 좋다. 별도 확정 문제 수에는 포함하지 않았다.

### 배열·편집·안전성

- **[실행 확인 — 격리]** `sanitize`의 비숫자 기본값, `0.2~20` clamp, 반올림, 표가 아닌 장의 배열 제거, 51개 배열 예외를 확인했다. `tableTracks`는 짧은 배열을 1로 채우고 여분을 버리며 행의 최솟값을 1로 맞췄다.
- 보통 비율의 2행 2열 표에서 중간 행·열 추가와 삭제를 실행하니 배열도 같은 자리에 추가·삭제됐다. 새 값은 이웃 값이었다. 결과의 `sanitize` 왕복과 [크기 같게]에서 두 속성 삭제도 통과했다. 극단 비율의 이웃 값·비대상 배열 유지 문제는 문제 2에 해당한다.
- **[정적 확인]** 덱 불러오기·발표 폴더·브라우저 저장본은 공통 검증을 거친다. 복제는 장 객체의 JSON 복사여서 비율도 보존한다. 형태를 표가 아닌 것으로 바꾸면 두 배열을 지운다. 배열의 숫자는 검증 후 CSS 숫자로 직렬화되므로 이번 경로에서 HTML/CSS 속성 주입은 발견하지 못했다.
- 소수 둘째 자리 저장은 작은 경계 이동을 양자화한다. 반복 반올림에 의한 미세 변화는 있을 수 있지만, 이번에 재현한 큰 변화는 반올림 자체가 아니라 개별 clamp 때문이다. 반복 편집 안정성 시험도 극단 비율을 포함해야 한다.

### 검사·문서·회귀

- **[실행 확인 — 격리]** 긴 설명 열을 가진 합성 표에서 `colW`가 없으면 추천 비율 경고가 나오고 `[1,3]`을 넣으면 그 추천 경고가 사라졌다. 좁은 열별 줄바꿈을 별도로 추정하는 변경은 반영돼 있다. `rowH` 높이 누락은 문제 3이다.
- 열 폭 계산의 패딩 50px과 최소 내용 폭 20px은 어림값이다. 실제 패딩은 em 단위이고 `fitBox`에 따라 바뀌므로 정확한 레이아웃 판정으로 보아서는 안 된다. 추천 비율은 최대 4로 제한된다.
- 문서는 글 길이 차이가 “2배 넘게”라고 쓰지만 코드는 `>= 2`여서 정확히 2배도 경고한다. 낮은 우선순위로 기준 문구를 “2배 이상”으로 맞추면 된다.
- 두 스킬 문서는 바이트 단위로 같고 열 너비·행 높이와 보존 규칙을 설명한다. README의 “위 행만 높이가 바뀐다”·“이웃과 같은 크기” 설명은 문제 2와 추가 fr 위험을 해결하거나 검증한 뒤 확인해야 한다. 버전과 AGENTS.md 이력은 `1.11.0`이다.
- **[실행 확인 — 격리]** 기본 13장의 `slideHTML` 문자열이 `main`과 전부 같았다. `app.js`, `deck-spec.js`, `check-deck.mjs`의 `node --check` 및 `git diff --check`도 통과했다. HTML 일치는 화면·글자 맞춤·인쇄 품질 검증을 대신하지 않는다.
- 시험은 원본 함수를 Node VM에서 실행하며 DOM·이벤트·치수를 대역으로 제공했다. 검사 스크립트용 합성 덱만 운영체제 임시 폴더에 만들고 종료 시 제거했다. 사용자 덱·생성기록·바탕화면은 건드리지 않았다. 요청서의 실제 Chrome 마우스·미리 보기·캡처 결과는 선행 작업자의 보고로만 취급했다.

## 의견 (우선순위 순서)

1. **앱이 스스로 열지 못하는 덱을 저장하지 않게 한다(문제 1).** 한도 검증을 조작 전 단계와 검증기에서 통일한다.
2. **비율 저장 표현을 통일한다(문제 2).** 대상 외 비율이 바뀌지 않도록 공통 배율 정규화와 반올림 정책을 적용한다.
3. **행 끌기의 실제 높이를 후속 검증한다.** 자동 높이 fr·내용 최소 높이·글자 맞춤이 겹치는 비대칭 사례가 필요하다. 모델상 위험을 브라우저에서 확인하기 전에는 “그 행만”이라는 동작을 확정하지 않는다.
4. **행 비율을 검사 스크립트 높이 추정에 반영한다(문제 3).** 이후 기준 문구와 안내를 맞춘다.

확정 문제 3건과 별도 검증이 필요한 행 높이 위험을 구분해 기록했다. 소스 수정·커밋·Chrome 실행·외부 전송은 하지 않았다.
