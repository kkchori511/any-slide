## 문제 목록

### 1. 중간 — 발표 폴더를 편집한 뒤 다시 ZIP으로 옮기면 편집 전 덱이 열림

- **위치:** `app/app.js:32–36`, `app/app.js:61–65`, `app/app.js:1309–1310`; `.claude/skills/slide-deck/scripts/pack-deck.mjs:29–44`, `pack-deck.mjs:83–88`.
- **증상:** 편집은 브라우저 localStorage에 저장되지만 동봉 JSON/deck-data.js에는 반영되지 않는다. `--zip-folder`는 디스크 파일만 압축한다. 따라서 폴더의 초기 배포 내용은 이동 가능하지만, 그 폴더를 열어 편집한 최신 내용까지 함께 이동하는 기능은 아니다.
- **근거:** [실행 확인 — 격리] 동봉 제목 ‘배포 원본’으로 시작하여 ‘현장 수정’으로 변경하고 실제 save/flushSave를 호출했다. 같은 저장소의 loadDeck은 ‘현장 수정’을 읽었다. 동일한 PACK 데이터를 빈 저장소의 새 실행 문맥에서 열면 ‘배포 원본’이었다. [정적 확인] ZIP 스크립트에는 브라우저 저장소나 새로 내려받은 JSON을 deck-data.js에 반영하는 단계가 없다.
- **범위:** 원래 컴퓨터의 localStorage에서 편집 내용이 삭제됐다는 뜻은 아니다. 재배포본에 최신 편집이 포함되지 않는 문제다. README의 ‘폴더째 다른 컴퓨터로 옮겨도 그대로’ 안내만으로는 이 차이를 알기 어렵다.
- **수정 제안:** ‘현재 편집본으로 발표 폴더/ZIP 내보내기’ 경로를 제공하거나, 최신 JSON을 저장한 뒤 그 JSON으로 pack-deck를 다시 실행하는 절차를 명시한다. JSON 파일만 폴더에 넣어서는 자동으로 읽지 않으므로 deck-data.js도 함께 갱신해야 한다. 초기 배포본과 브라우저 편집본의 차이를 UI와 README에 알린다.

### 2. 중간 — `.NET`처럼 점으로 시작하는 제목은 필수 덱 JSON이 ZIP에서 누락됨

- **위치:** `.claude/skills/slide-deck/scripts/pack-deck.mjs:40`, `pack-deck.mjs:71–75`, `pack-deck.mjs:83`.
- **증상:** safeTitle은 선행 점을 허용한다. `.NET 강의`는 `.NET_강의_v1` 폴더와 `.NET_강의_v1.json`을 만든다. ZIP 작성은 점으로 시작하는 파일을 모두 제외하므로 필수 덱 JSON까지 빠진다. macOS에서는 폴더 자체도 숨김 이름이다.
- **근거:** [실행 확인 — 격리] 실제 스크립트에 `--title '.NET 강의' --dest <임시경로> --zip`을 전달했다. 생성은 성공했으나 ZIP의 `.json` 항목은 0개였다. 일반 제목 ZIP에는 `<제목>_v1.json`이 들어 있었다. deck-data.js는 남으므로 앱 초기 실행 데이터까지 전부 없어지는 것은 아니다.
- **수정 제안:** 파일용 제목에서 선행 점을 정규화하고 빈 결과도 검증한다. 또는 필수 배포 파일을 명시적으로 포함하고, 숨김 제외는 메타데이터 등 불필요한 파일에만 적용한다. 화면용 원래 제목과 파일용 이름을 분리하면 좋다.

### 3. 중간 — 손상된 동봉 PACK 덱을 경고 없이 기본 예제로 대체

- **위치:** `app/app.js:9–11`, `app/app.js:51`, `app/app.js:1329–1330`.
- **증상:** PACK 객체는 있으나 deck 검증에 실패하면 예외를 삼키고 기본 13장 덱으로 돌아간다. localStorage 손상과 달리 loadWarning이 없어 사용자는 동봉 덱을 못 읽었다는 사실을 알기 어렵다.
- **근거:** [실행 확인 — 격리] PACK={key:'bad',deck:{}}을 제공했다. initialDeck은 기본 13장을 반환했고 loadWarning은 빈 문자열이었다. 정상 pack-deck가 만든 파일에서는 발생하지 않았으며, 동봉 데이터의 구조가 손상되거나 수동 교체된 경우의 실패 처리다.
- **수정 제안:** 동봉 덱 검증 실패를 화면에 분명히 알리고, 원문 파일 재선택·JSON 불러오기·원본 재생성 방법을 안내한다. 기본 예제를 제공하더라도 복구 상태임을 표시한다. deck-data.js 자체의 로드 실패까지 감지하려면 패키지 HTML에 동봉 데이터가 필수라는 표시도 두는 방법이 있다.

### 4. 낮음 — 생성 기록 손상 시 스택 오류만 출력하고 패키징을 중단

- **위치:** `.claude/skills/slide-deck/scripts/pack-deck.mjs:72–73`, `pack-deck.mjs:91–93`.
- **증상:** 생성 기록의 JSON 문법·배열 여부·항목 구조를 검증하거나 오류를 잡지 않는다. 문법이 틀리면 SyntaxError, `{}`이면 records.filter TypeError가 발생한다.
- **근거:** [실행 확인 — 격리] 임시 복사본의 기록을 `{broken`과 `{}`로 각각 바꿔 실행했다. 둘 다 종료 코드1과 Node 스택 오류를 반환했다. 폴더 복사 전 중단되며 기존 기록·발표 폴더를 덮어쓰지 않는 점은 안전하다.
- **수정 제안:** 기록 문법과 스키마를 확인하고 원문을 보존한 상태로 명확한 오류/복구 경로를 제공한다. 손상 시 무조건 빈 기록으로 덮어써 버전 충돌을 만들지는 않는다. 쓰기에는 임시 파일 후 교체를 사용하고, 동시에 여러 pack 작업을 지원한다면 기록 갱신의 충돌 방지도 추가한다.

## 요청 항목별 확인 결과

### 정렬 통일

- [실행 확인 — 격리] groupAlign은 빈 문자열·undefined·공백만 있는 칸을 판단에서 제외했다. 모두 비어 있거나 짧으면 center, 긴 글이나 목록이 하나라도 있으면 left였다.
- 카드 3개 중 하나가 길 때 c1/c2/c3 모두 left가 됐다. 긴 카드가 hidden이면 그 카드는 묶음에서 제외되어 나머지는 center였다.
- 표는 첫 줄을 제외한 데이터로 열별 정렬을 계산했다. 긴 머리글이 있는 열이라도 본문이 짧으면 center였고, 긴 본문이 있는 다른 열은 left였다. 머리 줄의 기본 가운데 정렬 경로는 유지된다.
- 실제 refreshAutoAligns를 호출해 두 상자의 자동값이 함께 갱신되는 것을 확인했다. left 필드에 명시적인 align:right가 있으면 오른쪽 정렬을 유지했고, 나머지 상자는 자동 left로 바뀌었다. 수동 설정을 제거하고 내용을 짧게 바꾸면 둘 다 center로 돌아왔다.
- [정적 확인] 입력 시 편집 DOM을 통째로 교체하지 않고 data-align0/textAlign을 바꾼다. 실제 커서·한글 입력·자동 정렬 전환의 시각적 흔들림은 브라우저에서 확인하지 않았다.
- 수동 정렬은 통일보다 우선하므로 일부 칸만 수동 지정하면 정렬이 섞일 수 있다. 이는 스킬에 명시된 예외이며 확정 결함으로 분류하지 않았다. 표 수동 정렬은 styles.table 단위로 전체 셀에 적용된다.

### 발표 폴더·저장 키·덱 삽입

- [실행 확인 — 격리] 한글/공백이 있는 저장 경로와 제목 `특강 / "실습" : API?`에서 `특강_실습_API_v1`을 생성했다. 필수 앱 파일·assets·fonts·덱 JSON·deck-data.js가 존재했다. HTML은 deck-data.js를 deck-spec.js보다 먼저 로드했다.
- 같은 제목으로 다시 생성하면 v2였고 PACK.key는 v1과 달랐다. v3 위치에 이미 폴더와 확인용 파일을 만들어 둔 경우는 명확한 오류로 중단했고, 기존 파일과 기록도 그대로였다.
- 동봉 제목에 `</script>`와 U+2028을 넣어 생성한 deck-data.js를 Node vm에서 읽었다. 덱 문자열은 원문대로 보존됐다. 이 파일은 인라인 script가 아닌 외부 JS이므로 이전 미리보기의 HTML 종료 태그 탈출 문제와 구분해야 한다. 이번 삽입에서 임의 코드 실행 경로는 발견하지 못했다.
- PACK 저장 키가 있으면 그 키로 저장/로드하며, 키가 다른 두 PACK은 같은 저장소 대역에서도 섞이지 않았다. initialDeck/초기화는 동봉 원래 덱으로 돌아갔다.
- 생성 시 임의 접미사를 붙여 서로 다른 생성본의 키를 구분한다. 폴더를 그대로 복사하면 키도 그대로 복사된다. 파일 URL의 실제 localStorage 격리 방식, 같은 컴퓨터의 폴더 복사본 간 상호작용은 브라우저별 검증을 하지 않았다. 키가 디렉터리 경로를 동적으로 계산하는 방식은 아니다.
- 실패 도중 생긴 일부 복사본·ZIP 실패와 생성 기록의 원자성은 추가 검토 가치가 있다. 현재 순서는 폴더 생성 → 파일 복사 → 기록 쓰기 → 선택적 ZIP이며, ZIP 실패만으로 앞선 생성이 롤백되지는 않는다. 이미 생성한 폴더는 `--zip-folder`로 재압축할 수 있다.

### ZIP

- [실행 확인 — 격리] 정상 제목의 ZIP은 Python testzip 검사에서 오류가 없었다. 한글 경로 엔트리에 UTF-8 플래그가 설정돼 있었다.
- 같은 폴더를 재압축해도 출력 Any-Slide.zip 자체가 ZIP 안에 들어가지 않았다. 테스트로 추가한 숨김 파일과 숨김 하위 폴더도 제외됐다. 단, 이 제외 규칙이 필수 JSON을 누락시키는 사례는 문제2와 같다.
- 출력 ZIP 이외의 임의의 다른 ZIP 파일까지 모두 제외하는 규칙은 없다. 발표 폴더에 별도 ZIP을 추가하면 그것은 포함될 수 있다.
- Windows 탐색기에서 실제 압축 해제·Edge 실행을 확인하지 않았다. UTF-8 플래그와 압축 무결성 검사만으로 Windows 실기 확인을 대체했다고 주장하지 않는다.

### 텔레그램 — 코드만 검토

- send-telegram.mjs는 **실행하지 않았다**. --whoami도 호출하지 않았으며 `.env`를 열거나 토큰·채팅 ID 값을 확인하지 않았다. 네트워크 전송도 하지 않았다.
- [정적 확인] 코드에는 token을 직접 출력하는 로그가 없고, API의 실패 description과 catch의 e.message에는 hide 함수를 적용한다. hide는 토큰과 정확히 같은 문자열을 치환하며 에러 객체 전체/stack/요청 URL을 출력하지 않는다. 실제 서비스 응답이나 네트워크 계층에서의 모든 누출 가능성을 실증한 것은 아니다.
- 파일 크기는 읽기·FormData 생성 전에 `size > 50 * 1048576`으로 검사한다. 즉 52,428,800바이트를 초과하면 중단한다. 실제 API 서버가 이 경계의 파일을 받는지는 검증하지 않았다.
- HTTP 응답은 JSON으로 읽고 r.ok가 false이면 실패 종료한다. 파일 읽기·fetch·JSON 파싱 예외도 try/catch에서 실패 안내한다. 요청 타임아웃과 자동 재시도는 없으므로 연결이 오래 멈추는 상황은 향후 보완 대상이다.
- 설정 파서는 단순한 `KEY=value`와 바깥 따옴표를 처리한다. 실제 설정 파일 문법과 호환되는지는 값 비열람 원칙에 따라 확인하지 않았다.

## 의견: 우선순위 순서

1. **재배포에 포함되는 덱 상태를 명확히 한다.** 브라우저 편집본을 동봉 데이터로 내보내는 기능 또는 최신 JSON으로 폴더를 다시 만드는 절차를 제공한다. 다른 컴퓨터에서 ‘최신 내용’이 열린다는 기대와 실제 동작을 맞춘다.
2. **제목 정규화와 필수 배포 파일 보존을 보완한다.** 선행 점·정규화 후 빈 이름·Windows 파일명 제약을 확인하고, 필수 JSON을 숨김 제외 규칙이 제거하지 않게 한다.
3. **복구 안내를 정리한다.** 동봉 덱 검증 실패와 생성 기록 손상을 서로 구분하여 알리고 원문을 보존한다. 생성 기록은 검증/원자적 쓰기 방식을 권한다.
4. **후속 실기는 허용된 별도 환경에서 한다.** 자동 정렬 중 입력·포커스, file URL 저장소, Windows 압축 해제·열기, 허가된 시점의 텔레그램 오류/크기 경계 검증을 수행한다. 이번 검토에서는 금지한 실행을 하지 않았다.
