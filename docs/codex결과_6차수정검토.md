## 문제 목록

### 1. [중간] zip 이름은 NFC로 바꾸지만 덱의 그림 참조는 NFD로 남음

- **위치:** `.claude/skills/slide-deck/scripts/pack-deck.mjs:50`, `:118–127`
- **증상:** NFD 한글 파일 이름을 `img` 또는 스티커에서 참조하는 덱은 패키징에 성공한다. 그러나 압축 후 그림 파일 이름은 NFC가 되고, 덱 JSON과 `deck-data.js`의 참조는 원래 NFD 문자열로 남는다. 따라서 압축 내부에서 참조와 정확히 일치하는 파일이 없다. 유니코드 정규형을 구별하는 대상 환경에서는 그림이 빠질 수 있다.
- **근거 [실행 확인 — 격리]:** `한글 그림.png`를 NFD로 분해한 실제 그림 파일과, 같은 NFD 경로를 그림 칸·스티커에 사용한 합성 덱으로 `--zip`을 실행했다. 종료 코드 `0`이었지만 Python `zipfile`의 엔트리 목록에는 `media/한글 그림.png`의 NFC 이름만 있었다. `deck-data.js`에서 읽은 `img` 경로와 정확히 일치하는 엔트리는 없었고, 그 경로를 NFC로 바꿔 비교하면 일치했다.
- **근거 [정적 확인]:** 그림 복사, 덱 JSON 저장, pack 저장에는 정규화가 없다. Python의 `z.write`에서 압축 엔트리 이름만 정규화한다. `--zip-folder` 역시 파일 내용은 바꾸지 않는다. 과거 NFD 폴더의 JSON 파일 이름을 NFC로 바꿀 때도 pack의 기존 `name` 또는 `title`과 불일치할 여지가 있다.
- **확인 한계:** Windows에서 직접 압축을 풀거나 브라우저로 그림을 표시하지 않았다. 이번 실행은 아카이브 이름과 참조 문자열의 불일치를 확인한 것이다. Mac에서 열리는 것만으로 다른 운영체제의 경로 일치를 보장할 수 없다.
- **수정 제안:** 패키징할 그림 파일 이름과 덱의 `img`·스티커 `src`를 같은 매핑으로 함께 NFC화한다. 정규화 후 이름이 겹치면 중단하고 알린다. 기존 폴더 압축은 원본을 바꾸지 않는 임시 배포 복사본에서 관련 참조도 함께 변환하거나, 불일치를 감지해 중단하는 정책을 권한다. 파일 이름만 바꾸는 방식은 피한다.
- **영향·확인:** NFD 그림, NFC 그림, 영문 그림과 정규화 충돌 사례를 시험한다. JSON·pack의 모든 그림 참조가 zip 엔트리에 정확히 대응하는지 검사하고, 이후 Windows에서 실제 표시를 확인한다.

### 2. [중간] 제목에서 금지 문자를 지운 뒤에는 NFC를 다시 적용하지 않아 버전 계산이 깨질 수 있음

- **위치:** `.claude/skills/slide-deck/scripts/pack-deck.mjs:65`, `:91`, `:103–104`
- **증상:** 정규화 뒤 금지 문자를 제거하면서 새로운 조합 가능 문자가 이어지면 최종 제목이 NFC가 아니다. 첫 생성 기록에도 비정규화 제목이 저장된다. 다음 실행에서는 기록만 NFC로 바꿔 비교하므로 자기 기록을 찾지 못하고 다시 v1을 선택해 기존 폴더 오류로 중단한다.
- **근거 [실행 확인 — 격리]:** 제목을 `ᄀ/ᅡ`(`U+1100`, `/`, `U+1161`)로 줬다. `/` 제거 후 `safeTitle`과 기록의 제목은 `가`로, NFC인 `가`와 달랐다. 첫 패키징은 성공했지만 같은 제목으로 다시 실행하면 v2가 아닌 `가_v1`을 선택하고 “같은 이름의 폴더가 이미 있음”으로 실패했다. 일반 NFD 완성형 제목 입력은 정상 통과하므로, 문자를 제거하는 순서에서 생기는 경계값 문제다.
- **수정 제안:** 제목의 trim·금지 문자 제거·공백 치환을 끝낸 **최종 결과**에 `.normalize('NFC')`를 적용하고 이를 이름·기록·비교에 공통으로 사용한다. 정리 전 입력을 정규화하는 것만으로는 충분하지 않다.
- **영향·확인:** 금지 문자로 나뉜 조합형 자모와 결합 문자를 시험한다. 같은 제목을 두 번 만들면 최종 이름이 NFC이고 버전이 증가하는지 확인한다.

### 3. [낮음] 마지막에 값 없이 준 `--date`가 오류 없이 무시됨

- **위치:** `.claude/skills/slide-deck/scripts/pack-deck.mjs:29`, `:66`, `:73–76`
- **증상:** `... --date`처럼 옵션 값이 없으면 명시한 날짜 옵션이 잘못됐다는 오류 대신 파일 이름 날짜 또는 날짜 없는 이름으로 성공한다. 사용자 의도와 다른 발표 날짜가 기록될 수 있다.
- **근거 [실행 확인 — 격리]:** 날짜 없는 합성 덱으로 마지막 인자를 `--date`로 주자 종료 코드 `0`으로 날짜 없는 폴더가 생성됐다. `opt('--date')`가 `undefined`여서 검증 조건을 건너뛴다. 옵션 자체를 생략하는 정상 경로와 구분하지 못한다.
- **수정 제안:** `args.includes('--date')`와 값 존재 여부를 함께 검사해, 옵션을 명시했는데 값이 없으면 생성 전에 중단한다. 일반적인 인자 파서 도입 없이도 해당 경계값을 막을 수 있다.
- **영향·확인:** 옵션 생략, 값 누락, 빈 문자열, 다른 옵션이 바로 뒤에 오는 경우와 정상 날짜를 구분한다.

### 4. [낮음] 스킬 문서의 zip 제외 대상 설명이 코드와 다름

- **위치:** `.claude/skills/slide-deck/SKILL.md:97`, `.codex/skills/slide-deck/SKILL.md:97`; 구현 `.claude/skills/slide-deck/scripts/pack-deck.mjs:48`
- **증상:** 문서는 `.DS_Store`, `._*`, `Thumbs.db`, `desktop.ini`, `.git`“만” 뺀다고 설명하지만, 현재 코드는 최상위의 모든 `.zip`도 제외한다. `Any-Slide.zip`과 현재 출력 파일 외의 zip도 빠진다.
- **근거 [정적 확인]:** 기존 문구가 그대로 남아 있다. **[실행 확인 — 격리]:** 최상위 `Any-Slide.zip`과 `EXTRA.ZIP`는 제외됐고 하위 `sub/keep.zip`은 포함됐다. 구현은 이번 요청의 최상위 zip 제외 정책과 일치한다.
- **수정 제안:** 두 문서에 “최상위 zip은 모두 제외하고 하위 폴더의 zip은 유지한다”를 명시한다. 코드 변경은 필요하지 않다.

## 추가 확인 결과

### 격리 방식과 정상 사례

임시 루트에 원본 `pack-deck.mjs`·`media.mjs`와 앱 코드 파일을 그대로 복사했다. 합성 덱과 1픽셀 PNG를 임시 입력 폴더에 만들고, `--dest`와 생성기록 경로도 임시 루트 안에 두었다. `assets/`·`fonts/`는 빈 대역 디렉터리이므로 전체 배포 에셋·글꼴 검증은 아니다. 원본 사용자 자료는 읽을 필요가 없었으며, 임시 루트는 `finally`에서 제거했다. 원래 `decks/생성기록.json`을 변경하지 않아 복구할 내용도 없다.

| 항목 | 확인 결과 |
| --- | --- |
| 파일 이름의 날짜 | `2026-10-28_발표.json` → `2026-10-28_<제목>_vN`, `presentDate:2026-10-28` |
| 명시 날짜 우선 | 같은 덱에 `--date 2026-11-01`을 주면 그 날짜 사용 |
| 날짜 없는 덱 | 날짜 없는 이름과 경고로 생성, 기록에서 `presentDate` 생략 |
| 날짜와 버전의 관계 | 같은 제목으로 날짜를 바꾸거나 날짜를 생략해도 v2 → v3 → v4 증가 |
| 과거 NFD 제목 기록 | NFD 제목의 기존 기록과 NFC/NFD 입력이 일치해 다음 버전 선택 |
| NFD `--dest` | NFD 저장 경로 안에 정상 생성. 기존 부모 경로를 강제로 바꾸지 않음 |
| 생성 메타데이터 | 폴더 이름·덱 JSON 이름·`pack.name` 일치, 기록의 발표일과 생성일은 별도 필드 |
| zip 이름과 엔트리 | 정상 한글 제목에서 zip 이름·모든 엔트리 이름 NFC, 비ASCII 엔트리에 UTF-8 플래그 |
| 반복 `--zip-folder` | 기존 zip을 다시 넣지 않음; 최상위 대문자 `.ZIP`도 제외, 하위 zip은 유지 |
| 경로 끝의 `/` | 없음·`/`·`///` 모두 최상위 zip 제외 동작 동일 |
| 기존 NFD 폴더 압축 | 끝에 `///`를 붙여도 압축 성공, zip 파일의 basename과 엔트리는 NFC |

**날짜 경계값 [실행 확인 — 격리]:** `2026-02-30`, `2025-02-29`, `1900-02-29`, 월 00·13, 일 00, 한 자리 월, 날짜 뒤 추가 문자를 거부했다. `2024-02-29`, `2000-02-29`, `0000-01-01`, `9999-12-31`은 허용했다. 연도 0000 허용은 JavaScript ISO 날짜 규칙에 따른 현재 동작이며, 별도의 업무상 연도 제한 요구가 없어 결함으로 세지 않았다.

**파일 이름 추출 [정적 확인]:** basename의 맨 앞 `YYYY-MM-DD_`만 후보로 삼으며 유효한 날짜일 때 사용한다. 잘못된 파일 이름 날짜는 날짜 미확인 경고 후 생략하고, 명시한 잘못된 `--date`는 중단한다. 확장자나 상위 폴더 이름에서 날짜를 잘못 꺼내는 구조는 아니다.

**zip 경로 비교 [정적 확인]:** 두 진입점 모두 절대 경로를 사용하고 `--zip-folder`는 끝의 `/`도 제거한다. Python `os.walk(folder)`의 첫 `dp`는 전달한 `folder`이므로, 시험한 경로 모양에서 `dp == folder`가 어긋나는 문제는 없었다. `--dest`의 부모 이름을 일괄 NFC로 바꾸는 것은 기존 경로 조회를 깨뜨릴 수 있으므로 권하지 않는다. 새로 만드는 basename과 zip 내부 상대 경로를 구분해야 한다.

### `packName()`·[폴더에 저장]·위험한 이름

- **[실행 확인 — 격리]** 실제 `packName`과 `saveToFolder`를 VM에서 실행하고 디렉터리·파일 쓰기를 메모리 대역으로 제공했다. 새 `PACK.name`은 JSON 파일 이름과 다시 저장한 pack에 그대로 유지됐다. 이름이 없는 과거 pack은 `<제목>_v<버전>`으로 저장됐으며, `name`이 빈 문자열 또는 숫자이면 같은 fallback을 사용했다. pack이 없으면 저장하지 않았다.
- **[정적 확인]** 정상 생성 경로의 `name`은 검증된 날짜와 `safeTitle`, 정수 버전을 조합한다. 제목의 `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`는 제거하고 공백류는 `_`로 바꾸므로, 생성된 `name`을 통해 상위 경로가 들어가는 문제는 발견하지 못했다. NFC 적용 순서는 문제 2에 해당한다.
- `packName()` 자체는 임의의 비어 있지 않은 문자열을 신뢰하며 별도 파일 이름 검증을 하지 않는다. 다만 `PACK`은 일반 덱 JSON이 아니라 실행되는 `deck-data.js`에서 오고, 일반 JSON [불러오기]가 `PACK.name`을 바꾸지는 않는다. 따라서 이를 이번 변경의 독립적인 외부 입력 보안 결함으로 보지는 않았다.
- 수작업으로 메타데이터에 구분자·줄바꿈 등을 넣으면 저장 오류나 주석 파손 가능성이 있다. 방어를 추가한다면 `deck-data.js`를 쓰기 **전에** 메타데이터 이름의 유효성을 확인하는 방식이 좋다. 현재는 메타데이터 파일을 먼저 쓰고 JSON 파일을 쓰므로 이름 오류가 뒤늦게 발생하면 저장이 일부만 반영될 수 있다. 실제 브라우저 파일 API로 이 경우를 실행하지는 않았다.
- 기존 NFD pack을 압축할 때 파일 이름만 바뀌고 메타데이터는 유지되는 경우의 정합성은 문제 1과 같은 원칙으로 처리해야 한다. 새 폴더의 정상 이름 저장 호환성 시험과 과거 파일 전체의 정규화 이행은 별개의 범위다.

### 문서·전송 코드·검증 한계

- 두 스킬 문서는 바이트 단위로 같고, 날짜 우선순위·날짜 생략·제목별 버전 계산·새 zip 이름·수신 파일 이름 NFC 안내는 구현과 대체로 맞는다. 제외 대상 설명은 문제 4에 해당한다.
- **[정적 확인]** `send-telegram.mjs:41–42`는 원래 경로로 파일을 읽고 multipart 파일 이름만 `basename(...).normalize('NFC')`로 보낸다. 로컬 NFD 경로를 잘못 NFC로 바꿔 읽는 문제는 없다. 이 스크립트는 **실행·import하지 않았고**, 봇 설정·토큰도 읽지 않았다. 수신 결과는 확인하지 않았다.
- 버전 `1.8.0`과 기본 덱 `sanitize` 후 13장 유지를 Node에서 확인했다. `app.js`, `deck-spec.js`, `pack-deck.mjs`의 `node --check` 및 `git diff --check`도 통과했다.
- 요청서의 Chrome PDF·캡처 결과는 선행 작업자의 보고이며 이번에 재검증한 결과가 아니다. Windows 압축 해제·브라우저 경로 처리·실제 폴더 저장·텔레그램 수신도 이번 검토에서 확인하지 않았다.

## 의견 (우선순위 순서)

1. **그림 파일 이름과 덱 참조를 함께 정규화한다(문제 1).** Windows 전달 목적에 직접 영향을 주는 항목이다. 압축 엔트리가 NFC인지뿐 아니라 모든 참조와 실제 이름이 일치하는지 확인해야 한다.
2. **최종 제목에 NFC를 적용해 버전 비교의 기준을 통일한다(문제 2).** 정리·정규화·기록·재실행까지 묶어 검사한다.
3. **`--date` 값 누락과 zip 제외 문서를 보완한다(문제 3·4).** 정상적인 날짜·압축 경로의 동작을 바꿀 필요는 없다.
4. **정상 확인 범위는 유지한다.** 날짜 추출·버전 증가·이름 저장 호환·최상위 zip 제외는 이번 시험에서 정상이다. 기존 메타데이터를 수작업으로 바꾼 경우와 운영체제 간 이행은 별도 후속 검증으로 다룬다.

이 문서는 검토와 제안만 담았다. 소스 수정·커밋·Chrome 실행·외부 전송은 하지 않았다.
