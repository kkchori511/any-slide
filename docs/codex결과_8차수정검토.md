# 8차 수정 검토 결과 (v1.10.0)

## 요약

- `main`(`9489b1e`)과 `user-images`(`5f4890b`, 검토 시 HEAD)의 차이를 코드 읽기와 Node 격리 실행으로 검토했다.
- 기존 저장 실패 상태에서 그림 추가가 되돌려지지 않는 문제, 잘못된 base64가 검증을 통과해 렌더링 예외를 내는 문제를 재현했다.
- 비동기 그림 처리가 다른 장·다른 덱으로 넘어가는 문제와 덱 교체 후 Blob 캐시 누적, 도움말·정보 패널의 동시 열림도 확인했다.
- 정상적인 중복 그림 재사용·전체 참조 삭제·붙여넣기 분기·변환 제어 흐름은 시험을 통과했고, 기본 13장의 생성 HTML은 `main`과 같았다.
- 결과 문서 외 파일은 수정하지 않았다. Chrome·미리 보기·텔레그램 실행, 외부 전송, 사용자 덱·생성기록·바탕화면 변경은 하지 않았다.

## 문제 목록

### 1. [높음] 이미 자동 저장이 실패하고 있으면 새 그림 저장 실패를 되돌리지 않음

- **위치:** `app/app.js:1287–1303`; 저장 결과 관리 `:89–103`
- **증상:** 기존에 저장 공간 부족 등으로 `saveFailed=true`인 상태에서 그림을 넣으면, 이번 저장도 실패했는데 그림과 참조를 유지하고 성공(`true`)을 반환한다. 여러 파일 처리도 계속 진행할 수 있다. 화면에는 넣어진 것처럼 보이지만 자동 저장본에는 남지 않아 재시작 때 잃을 수 있다. 기존 자동 저장 경고는 나오지만 그림 추가 실패 전용 안내와 되돌리기는 생략된다.
- **근거 [정적 확인]:** 되돌리기 조건이 `saveFailed && !wasFailing`이다. 이번 저장의 성공 여부가 아니라 이전 실패 상태에서 새 실패 상태로 바뀌었는지만 검사한다.
- **근거 [실행 확인 — 격리]:** 실제 `placeUserImage`와 `flushSave`를 VM에서 실행하고 `localStorage.setItem`이 계속 실패하도록 했다. 이전 실패 상태가 `false`이면 반환값 `false`, 스티커 0개·그림 0개·전용 alert 1회였다. 이전 상태가 `true`이면 반환값 `true`, 스티커 1개·그림 1개·전용 alert 0회로 남았다.
- **수정 제안:** `flushSave`가 이번 호출의 성공·실패·저장 생략을 명시적으로 반환하도록 하고, 이번 추가를 저장하지 못했으면 이전 실패 상태와 무관하게 되돌린다. 이미지·그림 칸·스티커와 선택 상태를 스냅샷으로 복원하고, 이전 저장 오류 안내는 유지한다. `packBroken` 때문에 저장을 생략하는 경우도 성공으로 취급하지 않아야 한다.
- **확인 방법:** 이전 오류 없음/있음 각각에서 성공·실패·저장 생략을 시험하고, 여러 파일에서 첫 성공 뒤 실패하면 그 파일만 되돌리고 나머지는 중단하는지 확인한다.

### 2. [중간] base64 문자만 확인해 디코딩할 수 없는 그림이 검증을 통과함

- **위치:** `app/deck-spec.js:417–419`, `:432–437`; `app/app.js:1204–1213`, 초기 렌더링 `:1700–1710`
- **증상:** `data:image/png;base64,A`처럼 base64 길이·패딩이 잘못된 값도 `sanitize`가 유지한다. 이를 그림 칸·스티커로 그리면 `atob`가 예외를 던진다. 일반 JSON 불러오기는 렌더링 검사에서 잡을 수 있지만, 브라우저 저장본·발표 폴더의 초기 덱은 검증을 통과한 뒤 초기 렌더링에서 중단될 수 있다.
- **근거 [실행 확인 — 격리]:** 실제 `isUserImgData`, `sanitize`, `srcURL`, `userImgURL`을 Node VM에서 실행했다. payload `A`, `AAAAA`, `A=`는 모두 허용·보존됐으나 `srcURL('user:u1')`에서 `InvalidCharacterError`가 발생했다. 패딩이 3개인 값은 거부됐다.
- **근거 [정적 확인]:** 정규식은 허용 문자와 끝의 `=` 개수만 검사한다. `userImgURL`의 `atob`에는 예외 처리가 없고, 시작 시 `go(...)`도 덱 읽기 예외 처리 밖이다. 파일 추가의 canvas 출력은 정상 base64를 생성하지만, 외부 덱·기존 저장본은 그 변환 경로를 거치지 않는다.
- **수정 제안:** 파서와 실제 디코더의 허용 조건을 맞춰 base64 길이·패딩을 검증한다. URL 생성 실패도 잡아 잘못된 그림 때문에 전체 앱이 중단되지 않도록 한다. base64 디코딩 가능 여부와 실제 PNG/JPEG/WEBP 이미지인지 여부는 별도로 구분한다.
- **확인 방법:** 4로 나눈 나머지가 1인 payload, 잘못된 패딩, 정상 패딩·무패딩의 허용 정책을 검사한다. 불러오기뿐 아니라 브라우저 저장본과 발표 폴더 초기 렌더링 경로도 확인한다.

### 3. [중간] 그림 변환을 기다리는 동안 장·덱을 바꾸면 새 대상에 그림이 들어감

- **위치:** `app/app.js:1255–1261`, `:1279`; 파일 입력 `:1611–1614`, 덱 교체 `:1675–1693`
- **증상:** 파일 선택·붙여넣기를 시작한 장이 아닌 다른 장에 그림이 들어갈 수 있다. 처리 중 [불러오기]·[초기화]를 하면 교체된 덱에 이전 작업의 그림이 추가되고, 발표 모드로 바꿔도 뒤늦게 추가된다. 여러 파일도 각 변환 완료 시점의 전역 `deck`·`cur`를 사용한다.
- **근거 [정적 확인]:** `await fileToUserImage` 전에 덱·대상 장·작업 세대를 고정하지 않는다. 완료 후 `placeUserImage`가 현재 전역 상태를 읽으며 모드·대상 변경을 확인하지 않는다. 같은 시점의 여러 추가 작업도 별도로 직렬화하지 않는다.
- **근거 [실행 확인 — 격리]:** 실제 `addUserImages`·`placeUserImage`에서 파일 변환만 지연 Promise로 대체했다. 완료 전 `cur=1`과 발표 모드로 바꾸자 원래 0번이 아닌 1번 장에 그림 칸 참조가 생겼다. 다른 실행에서 완료 전 덱 객체를 교체하자 새 덱에 스티커가 추가됐다.
- **수정 제안:** 추가 시작 시 덱·대상 장을 고정하고 덱 교체 시 작업을 취소하는 세대 값을 둔다. 장이 삭제됐거나 모드가 바뀐 경우의 취소 정책도 정한다. 여러 추가 요청은 같은 대상에 대해 순서대로 처리하고, 새 덱에 조용히 넘어가지 않게 한다.
- **확인 방법:** 변환 대기 중 장 이동·삭제, 덱 불러오기·초기화, 발표 전환, 연속 붙여넣기를 시험한다.

### 4. [중간] [불러오기]·[초기화] 후 이전 덱의 Blob 캐시를 정리하지 않음

- **위치:** `app/app.js:1203–1215`, `:1675–1693`; 명시적 삭제 정리 `:1315–1316`
- **증상:** 덱을 바꿔도 이전 그림의 data 문자열과 Blob URL을 캐시가 계속 보유한다. 서로 다른 ID를 가진 덱을 반복해서 열면 현재 덱의 그림 수 제한 60개와 무관하게 메모리 사용이 누적된다.
- **근거 [정적 확인]:** 캐시 해제는 같은 ID의 데이터가 바뀌었을 때와 [내 그림]의 ✕ 삭제에만 있다. 덱 교체·초기화에는 정리가 없다. 더 이상 없는 ID로 조회해도 캐시를 제거하지 않는다.
- **근거 [실행 확인 — 격리]:** 한 장·한 그림씩인 덱 70개로 전역 `deck`을 차례로 교체하고 실제 `userImgURL`을 호출했다. 캐시 크기 70, URL 생성 70회, 해제 0회였다. 각 덱 자체는 그림 수 제한 이내다.
- **수정 제안:** 성공적으로 덱을 교체할 때 이전 캐시를 해제하거나, 현재 덱이 소유한 그림만 유지하는 덱별 캐시로 관리한다. 후보 덱의 렌더링 검사가 실패했을 때도 캐시를 함께 복구·정리한다. 인쇄용 DOM이 사용 중인 URL은 작업 종료까지 유지하도록 수명을 구분해야 한다.
- **확인 방법:** 덱 반복 불러오기·초기화·실패한 불러오기 후 URL 생성/해제 수를 검사한다. 인쇄 중 덱 교체·삭제가 가능한 환경에서는 출력이 사용하는 URL을 너무 일찍 해제하지 않는지도 확인한다.

### 5. [낮음] 도움말을 연 뒤 정보 버튼을 누르면 두 패널이 함께 열림

- **위치:** `app/app.js:1621–1638`
- **증상:** 도움말을 열 때는 정보 팝업을 닫지만, [Any-Slide] 정보 버튼을 누를 때는 도움말을 닫지 않는다. 요청서의 패널 상호 닫힘이 한 방향에서 빠졌다.
- **근거 [정적 확인·실행 확인 — 격리]:** 실제 버튼 처리기를 DOM 대역에 연결해 [? 도움말] → [Any-Slide] 순서로 호출하자 `helpPanel.hidden=false`, `aboutPop.hidden=false`가 함께 유지됐다.
- **수정 제안:** 정보 팝업을 열 때 도움말도 닫거나, 공통 패널 열기 함수를 사용해 상호 배타 규칙을 일관되게 적용한다.
- **확인 방법:** 도움말·정보·스티커·설정을 양방향 순서로 열고, Esc 처리도 함께 확인한다.

## 정상 확인과 추가 의견

### 보안·검증·비용

- **[정적 확인·실행 확인 — 격리]** SVG·HTML data 주소, 외부 URL, 따옴표·세미콜론을 넣은 payload는 거부했다. 잘못된 ID, 없는 `user:` 참조도 제거했다. 정상 그림·그림 칸·스티커의 `sanitize` 왕복은 유지됐고 유효 그림 61개는 예외로 거부됐다. ID 규칙상 `__proto__`·`constructor` 같은 객체 키는 사용할 수 없다.
- 그림 칸·스티커는 `srcURL`로 Blob 주소를 얻고 `esc`를 거쳐 큰따옴표 `src` 속성에 넣는다. data 문자열 자체를 HTML 속성으로 이어 붙이지 않는다. 패널의 그림은 DOM `img.src` 속성에 지정한다. 고정 형태 그림의 경로는 타입 정의에서 온다. 확인한 경로에서 HTML 속성 주입 문제는 발견하지 못했다.
- 파일 추가는 MIME 제한 후 canvas로 다시 그린 data만 사용한다. 클립보드 파일도 같은 변환을 거친다. [불러오기]·초기 pack·브라우저 저장본은 `sanitize`를 거치지만, 문제 2처럼 현재 검증이 디코딩 성공까지 보장하지는 않는다. `deck-data.js` 자체는 실행되는 JavaScript라는 기존 신뢰 경계도 유지된다.
- **[실행 확인 — 격리]** 정확히 300만 자인 정상 허용 문자 문자열은 약 4ms, 끝의 문자를 `!`로 바꾼 같은 길이 문자열은 약 8ms에 판정됐다. 300만 자 초과는 정규식 전에 거부했다. 이번 Node 환경에서는 스택 초과나 급격한 역추적 비용을 관찰하지 못했다. 브라우저별 성능 보장은 아니다.
- 덱 전체의 인코딩 데이터는 최대 60 × 300만 자까지 가능하다. 각 그림 제한과 자동 저장 용량은 별개이며, 큰 외부 덱을 읽을 때의 메모리·총량 정책은 추가 개선 여지다. 이를 이번 요구의 독립 결함으로 세지는 않았다.

### 저장·여러 파일·삭제

- **[실행 확인 — 격리]** 정상 저장 시 같은 data를 두 번 넣어도 그림 데이터는 1개만 유지되고 참조는 각각 추가됐다. 여러 장의 그림 칸과 스티커에 쓴 그림을 지우면 모든 참조가 제거됐고, 마지막 그림 삭제 시 빈 `images`도 제거됐다.
- 여러 파일에서 첫 번째 그림 칸 저장은 성공하고 두 번째 스티커 저장은 실패하도록 하자, 첫 성공은 유지되고 두 번째만 되돌려졌으며 세 번째는 처리하지 않았다. 이 정상 동작은 문제 1의 이전 오류 상태가 없다는 조건에서 확인했다.
- **[정적 확인]** 첫 실패의 되돌리기는 기존 그림 칸과 스티커 길이를 복구하고 선택은 `sel=-1`로 해제한다. 기존 선택 자체를 복원하지는 않는다. 스티커 수 제한으로 거부할 때 처음 만든 빈 `images={}`가 남을 수 있지만 저장된 참조는 없고 다음 `sanitize`에서 생략되므로 낮은 우선순위 정리 사항이다.
- 삭제의 사용 횟수는 각 그림 칸 1곳과 같은 그림을 사용하는 스티커 개수를 합한다. 캐시의 해당 URL도 해제한다. 현재 인쇄 정책은 Chrome 권장이고 실제 인쇄 중 조작 가능 여부는 시험하지 않았으므로, 해제 시점을 보완할 때 인쇄 수명도 함께 확인해야 한다.

### 변환·붙여넣기

- **[실행 확인 — 격리]** 실제 `fileToUserImage` 제어 흐름에 이미지 크기·canvas를 대역으로 제공했다. 3000×2000 입력은 1600×1067이 됐고, alpha가 있으면 PNG, 없으면 JPEG를 선택했다. 입력 파일용 임시 Blob URL은 성공 후 해제됐다. 실제 픽셀 변환·화질·투명도·GIF 장면은 검증하지 않았다.
- **[정적 확인]** 허용 크기를 넘으면 기준 변을 0.75배씩 줄이며, 작은 크기에서도 실패하면 예외로 중단한다. 모든 파일은 순차 변환하지만 다른 추가 요청과의 동시 진행은 차단하지 않는다(문제 3).
- **[실행 확인 — 격리]** 문서 캡처 단계의 실제 paste 처리기를 대역 이벤트로 시험했다. 편집 가능한 글자 칸에 일반 글자가 함께 있으면 그림 처리를 양보하고, 그림만 있으면 추가한다. INPUT·TEXTAREA·SELECT는 가로채지 않으며 발표 모드도 제외한다. 글자 칸 밖에서는 글자와 그림이 함께 있어도 그림을 넣는다. 그림 칸 선택 패널이 열려 있으면 `forSlot=true`로 전달됐다.
- 조건상 도움말·설정이 열려 있어도 그림 붙여넣기는 가능하고, 그림 칸 선택 패널이 아니면 스티커로 추가된다. 공백뿐인 텍스트는 `.trim()` 뒤 빈 값으로 취급한다. 실제 OS 클립보드·브라우저별 `files` 전달 방식은 확인하지 않았다.

### 도움말·문서·회귀 확인

- **[실행 확인 — 격리]** `PACK` 없음, `PACK` 있음+폴더 API 없음, `PACK` 있음+폴더 API 있음의 세 분기에서 실제 도움말 문구를 확인했다. [폴더에 저장] 버튼 노출·지원 여부의 기존 코드와 맞는다.
- **[정적 확인]** 스티커·설정 열기는 도움말을 닫고 도움말 열기도 다른 패널을 닫는다. 정보 버튼의 반대 방향 누락은 문제 5다. 입력·버튼 포커스에서 Esc는 먼저 blur하고 다음에 패널을 닫는 기존 키 처리 순서를 따른다.
- HTML 도움말·README의 JSON 내 그림 저장과 `media/` 외부 파일 구분은 구현과 맞는다. “저장 공간이 가득 차면 넣지 않는다”는 설명은 문제 1 때문에 현재 모든 상태에서 성립하지 않는다. 약 5MB는 브라우저별 제한을 단정하는 값이 아니라 대략적인 안내로 보아야 한다. 다운로드 폴더 위치도 사용자 설정에 따라 달라질 수 있다.
- 두 스킬 문서는 바이트 단위로 같고 `images`·`user:` 보존 안내가 있다. 바로 앞의 “목록 또는 media만 쓴다” 문장은 다음 예외 문장과 함께 읽으면 뜻이 통하지만, 새 덱 작성 제한과 기존 사용자 그림 보존을 구분하면 더 명확하다. 버전과 AGENTS.md 이력은 `1.10.0`이다.
- **[실행 확인 — 격리]** 실제 `slideHTML`로 기본 13장 모두의 HTML 문자열이 `main`과 같음을 확인했다. `node --check app/app.js`, `node --check app/deck-spec.js`, `git diff --check`도 통과했다. 화면·글자 맞춤·PDF·실제 파일 저장을 검증한 것은 아니다.
- 검토는 원본 함수를 읽어 Node VM에서 실행하고 DOM·저장소·URL 수명·지연 변환을 대역으로 제공했다. 사용자 덱과 바탕화면은 읽을 필요도 없었으며, 패키징 스크립트와 생성기록은 건드리지 않았다. 요청서의 Chrome 캡처·인쇄·pack·preview 결과는 선행 작업자의 보고로만 취급했다.

## 의견 (우선순위 순서)

1. **이번 저장의 결과를 기준으로 되돌린다(문제 1).** 기존 실패 상태를 이유로 추가를 성공 처리하는 경로를 먼저 막는다.
2. **base64 검증과 URL 생성의 예외 경계를 맞춘다(문제 2).** 초기 저장본·발표 폴더에서도 잘못된 한 그림이 앱 전체를 멈추지 않게 한다.
3. **그림 추가 작업을 덱·대상 장에 묶고 캐시 수명을 정리한다(문제 3·4).** 덱 교체 취소, 후보 덱 검사 실패, 인쇄 참조를 함께 다룬다.
4. **패널 열기 규칙을 통일한다(문제 5).** 도움말 문구는 저장 실패 보완 후 실제 동작에 맞춰 확인한다.

이 문서는 검토와 제안만 담았다. 소스 수정·커밋·Chrome 실행·텔레그램 등 외부 전송은 하지 않았다.
