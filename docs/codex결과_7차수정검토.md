# 7차 수정 검토 결과 (v1.9.0)

## 요약

- `main`(`8e20190`)과 `text-color`(`6d37d87`, 검토 시 HEAD)의 차이를 코드 읽기와 Node 격리 실행으로 검토했다.
- 검정·사용자 색·겹친 서식·이스케이프의 왕복 시험을 통과했고, 확인한 입력 경로에서 색 값을 통한 HTML 속성 주입 문제는 발견하지 못했다.
- 같은 색 재적용 경로의 부족과 도구 줄 재생성 시 색 입력의 포커스 복구 누락을 확인했다. 전자는 네이티브 선택창의 이벤트 발생 조건에 따른 위험으로 실제 브라우저 검증이 필요하다.
- 기본 13장의 생성 HTML은 `main`과 동일했고, 사용자 색을 넣은 13종의 HTML 생성과 `check-deck`의 본문·표 검사도 정상이다. 화면·인쇄 결과를 검증한 것은 아니다.
- 결과 문서 외 파일은 수정하지 않았다. Chrome·미리 보기 실행, 외부 전송, 사용자 덱·바탕화면 변경은 하지 않았다.

## 문제 목록

### 1. [중간] 값이 바뀌지 않아 `change`가 발생하지 않으면 같은 사용자 색을 다른 글자에 재적용할 수 없음

- **위치:** `app/app.js:1037–1048`, 특히 `:1042`, `:1044–1046`; 사용 안내 `app/README.md:24`
- **증상:** 사용자 색 A를 한 부분에 적용한 뒤 다른 글자를 선택하면 새 색 입력도 A로 초기화된다. 선택창에서 A를 그대로 확정해 값이 바뀌지 않는 경우에는 적용을 호출할 경로가 없다. 첫 기본값인 `#1a73e8`을 그대로 고르는 경우도 같다. 다른 색으로 바꿨다가 돌아오는 조작이 필요할 수 있다.
- **근거 [정적 확인]:** 입력은 항상 `lastPicked`로 초기화되고 `applyFormat`은 `change` 처리기 안에서만 호출된다. 마지막 색을 바로 적용하는 버튼이나 별도 확정 동작은 없다. `change`는 선택창 닫힘 자체를 나타내는 이벤트가 아니므로 “창을 닫으면 칠해진다”는 설명보다 적용 조건이 좁다.
- **근거 [실행 확인 — 격리]:** 실제 `colorPicker` 함수를 Node VM에 넣어 첫 입력에서 `#8a4fc8` 변경을 전달하자 적용이 한 번 호출됐다. 두 번째 입력은 같은 `#8a4fc8`로 시작했다. “값이 달라질 때만 `change`를 보내는 입력” 대역에서 같은 값을 확정하면 적용 호출은 늘지 않았다. 대역에서 이벤트를 임의로 보내면 같은 값도 정상 적용되므로 문제는 색 처리 자체가 아닌 적용 진입 조건이다.
- **근거 [추정]:** 실제 Chrome·Safari·Firefox의 네이티브 색 선택창이 동일 색 확정·취소·포커스 이탈에 어떤 이벤트를 보내는지는 이번에 확인하지 않았다. 따라서 특정 브라우저에서 실제 재현됐다는 뜻은 아니다.
- **수정 제안:** 마지막으로 고른 색을 현재 선택에 적용하는 명시적인 동작을 제공하고, 색을 바꾸는 선택창과 적용을 구분하는 방안을 권한다. 닫힘만으로 적용하려면 취소와 동일 값 확정을 구별할 정책이 필요하다. 단순히 모든 `blur`나 `click`에 적용하면 취소할 때 칠해질 수 있어 피한다.
- **확인 방법:** 같은 색을 서로 다른 선택에 연속 적용, 최초 기본 색 그대로 확정, 값 변경 후 확정, 취소, 키보드 확정을 실제 지원 브라우저에서 확인한다.

### 2. [낮음] 도구 줄 재생성 시 [다른 색] 입력의 키보드 포커스를 복구하지 않음

- **위치:** `app/app.js:1043`, `:1057–1065`
- **증상:** 색 입력에 포커스가 있는 상태에서 도구 줄을 다시 그리면 입력이 제거되고, 새 입력으로 포커스를 돌려주지 않는다. 같은 도구가 다시 생기는 경우에도 키보드 작업 위치를 잃는다.
- **근거 [정적 확인]:** 새 색 입력에 `dataset.key`를 부여하고 `renderCtx`도 그 키를 보관하지만, 복구 대상 검색은 `querySelectorAll('button')`만 사용한다. 새 컨트롤은 `input`이므로 검색되지 않는다.
- **근거 [실행 확인 — 격리]:** 실제 `renderCtx` 함수를 DOM 대역에서 실행했다. 기존 색 입력의 키를 보관하고 같은 키의 대체 입력이 존재하는 상황을 제공해도 `focus()`는 호출되지 않았다. 실제 브라우저에서 재생성이 발생하는 조작 순서와 네이티브 창 상태는 확인하지 않았다.
- **수정 제안:** 복구 검색에 색 입력 등 `data-key`를 가진 포커스 가능 컨트롤을 포함한다. 현재 편집 대상이 달라진 경우에는 이전 컨트롤로 복구하지 않도록 구분한다.
- **확인 방법:** 색 입력에 Tab으로 접근한 상태에서 같은 편집 대상의 도구 줄을 재생성하고 포커스가 대응 입력으로 돌아오는지 검사한다. 기존 버튼 포커스 복구도 함께 확인한다.

## 추가 확인 결과

### 색 값과 HTML 속성 안전성

- **[정적 확인]** 일반 본문·제목·표 등은 `markupToHTML → parseMarkup → textColor → runsToHTML` 경로를 탄다. `sanitize`는 글자 문자열을 그대로 보존하지만 실제 HTML을 만들 때 색 토큰을 다시 해석한다. JSON [불러오기], 브라우저 저장 덱, 발표 폴더 덱도 같은 렌더러를 사용한다.
- `runsToHTML` 자체는 `r.c`를 재검증하거나 속성 이스케이프하지 않는다. 다만 검색한 실제 호출은 `markupToHTML` 한 곳이고, 여기에 전달하는 runs는 `parseMarkup`의 결과다. 검증되지 않은 덱 색 값이 이 HTML 생성 지점으로 직접 들어오는 호출 경로는 찾지 못했다. 방어를 강화하려면 생성 함수에서도 `textColor`를 적용할 수 있으나, 현재 경로의 확정 취약점으로 세지는 않았다.
- **[실행 확인 — 격리]** `#ABCDEF`는 `#abcdef`로 정규화됐다. 짧은 hex, 8자리 hex, 따옴표를 섞은 목록 이름, 세미콜론·CSS 추가 값, `url(...)`, `__proto__`, `constructor`, 비문자열 값은 거부됐다. 색 표기 속 `<img ...>` 본문은 `&lt;img ...&gt;`로 이스케이프됐다. 따옴표·CSS를 섞은 잘못된 색 표기는 일반 글자로 렌더링됐다.
- **[정적 확인·실행 확인 — 격리]** `domItems`는 `.cx`의 `data-c`를 `textColor`로 검증한 뒤 runs에 넣는다. DOM 대역의 대문자 hex는 소문자로 저장되고 따옴표·CSS를 넣은 `data-c`는 색 없이 내용만 저장됐다. 임의의 `style.color`를 복사하지 않는다. 목록 색과 사용자 색이 중첩된 DOM은 안쪽 색 적용 후 바깥 색으로 복귀했다.
- 붙여넣기는 `text/plain`만 `insertText`로 받는다(`app/app.js:589–595`). 일반 텍스트의 표기 문자는 편집 DOM을 저장할 때 `runsToMarkup`이 이스케이프한다. 붙여넣은 HTML 속성을 색 경로로 그대로 전달하는 코드는 없다. 실제 브라우저의 붙여넣기·드롭·자동 생성 DOM 전체를 시험한 것은 아니다.
- 발표 폴더의 `deck-data.js`는 원래 실행되는 JavaScript 파일이다. 그 파일 자체를 임의 코드로 바꿀 수 있다는 사실과 이번 색 표기의 속성 주입 문제는 구분했다. 검토는 해당 파일에서 정상 덱 객체로 공급한 문자열이 공통 렌더러에서 안전하게 처리되는 경로를 확인했다.

- 편집·썸네일·발표·인쇄는 공통 슬라이드 렌더러를 사용한다. 검정 CSS와 사용자 색 inline style은 특정 모드에 한정되지 않는다. `fitText`도 같은 글자 DOM을 측정하므로 이번 색을 별도로 해석할 필요는 없다. 실제 글자 높이·PDF 출력 색·인쇄 설정 적용 여부를 검증한 것은 아니다.
- `preview-deck.mjs`는 앱 자체로 그리는 구조이므로 별도 색 파서를 추가할 필요는 없다. 이 스크립트는 Chrome을 실행하므로 실행하지 않았다.

### 선택창·키보드·문서와 검증 한계

- `lastRange`는 도구 줄로 선택이 옮겨간 뒤 live selection이 편집 칸 밖에 있으면 fallback으로 쓰인다. 이 조건에서 부분 색 적용은 대역 시험을 통과했다. 네이티브 창이 선택을 편집 칸 안의 collapsed range로 바꾸는 경우나 OS 포커스 이동까지 보존된다고 단정할 수는 없다.
- 색 입력은 도구 줄 안에 있으므로 일반적인 Tab 이동에서는 `leaveTextIfOutside`의 편집 대상 유지 조건에 포함된다. 기존 버튼과 달리 기본 포인터 동작을 막지 않는 것은 네이티브 색 입력 활성화와 함께 검토해야 한다. 기본 동작을 무조건 막는 수정을 권하지 않는다.
- `colorPicker`는 `change`마다 적용하며 별도의 중복 이벤트 방지나 명시적 취소 처리가 없다. 실제 Safari·Firefox에서 미리 보기·확정·취소·텍스트 입력 fallback이 어떤 이벤트를 내는지는 확인하지 않았다. “닫을 때 한 번만”이라는 주석과 안내는 검증 범위보다 단정적이다(문제 1).
- 두 스킬 문서는 바이트 단위로 같고, 검정·6자리 hex·plain 필드 예외 설명이 코드와 일치한다. `PALETTE.black`과 `.c-black`은 모두 `#1a1a1a`다. 앱 버전과 AGENTS.md 이력은 `1.9.0`이다.
- `node --check app/app.js`, `node --check app/deck-spec.js`, `git diff --check`는 통과했다. 요청서의 Chrome 편집·색 캡처·기본 덱 캡처 결과는 선행 작업자의 보고이며 이번 검증으로 재확인한 결과가 아니다.

## 의견 (우선순위 순서)

1. **같은 사용자 색을 다시 적용하는 동작을 보완한다(문제 1).** 마지막 색 적용과 색 변경을 구분하면 네이티브 창의 동일 값 이벤트에 덜 의존한다. 실제 브라우저의 확정·취소 동작을 확인한 뒤 안내 문구도 맞춘다.
2. **도구 줄의 포커스 복구 대상에 색 입력을 포함한다(문제 2).** 새 컨트롤에 부여한 `data-key`가 복구에도 사용되게 한다.
3. **공통 파서·렌더러 구조는 유지한다.** 이번 시험에서는 안전성·왕복·다른 처리 경로의 누락을 발견하지 못했다. 후속 실환경 확인은 동일 색 재사용, 키보드 선택, Safari·Firefox의 창 이벤트, 인쇄에 집중하면 된다.

이 문서는 검토와 수정 제안만 담았다. 소스 수정·커밋·Chrome 실행·텔레그램 등 외부 전송은 하지 않았다.
