# 5차 수정 검토 결과 (v1.7.0)

## 요약

- `main`(`2b89c56`)과 `print-button`(`2bdfd3a`, 검토 시 HEAD)의 차이를 코드 읽기와 Node 격리 실행으로 검토했다.
- [인쇄]에서 모든 장을 준비하는 단순화는 일관되게 반영됐고, 이번 변경으로 새로 생긴 결함은 발견하지 못했다.
- 삭제한 쪽 선택 코드의 실행 참조는 없으며, 과거 검토 문서와 이번 요청서에만 관련 식별자가 남아 있다.
- 준비 중 잠금·중복 호출 차단, 비동기 인쇄 반환 후 DOM 유지, `afterprint` 정리, 예외 복구, 3초 초과 경고는 대역 시험을 통과했다. 다만 인쇄 중 재진입을 허용하는 기존 위험 1건은 남아 있다.
- 소스·덱·생성기록은 수정하지 않았고 Chrome 실행·외부 전송도 하지 않았다. 실제 브라우저 출력과 이벤트 순서는 이번에 확인하지 않았다.

## 문제 목록

### 1. [중간] 비동기 인쇄가 끝나기 전 재실행하면 진행 중인 작업을 교체할 수 있음 — 기존 잔여 위험

- **위치:** `app/app.js:1261–1264`, `:1273–1280`, 정리 함수 `:1253–1259`
- **증상:** `window.print()`가 즉시 반환하고 인쇄가 아직 끝나지 않은 상태에서 다시 [인쇄]를 누를 수 있는 환경이면, 기존 쪽을 지우고 새 작업을 시작한다. 이후 이전 작업의 `afterprint`가 도착하면 새 작업의 쪽과 제목까지 정리할 수 있다.
- **근거 [정적 확인]:** 재진입 차단 조건은 `printJob && !printJob.printing`이므로 준비 중에만 차단한다. `printing = true`인 작업은 종료 여부를 따로 확인하지 않고 `endPrintJob()`으로 정리한다. 버튼도 `window.print()` 반환 직후 다시 활성화된다. `afterprint` 처리기는 특정 작업에 묶이지 않고 현재 전역 `printJob`을 정리한다.
- **근거 [실행 확인 — 격리]:** 실제 `buildPrintPages`·`printDeck`·`endPrintJob` 코드를 Node VM에 넣고 DOM·이벤트·인쇄를 대역으로 실행했다. 첫 인쇄가 반환했지만 `afterprint`는 보내지 않은 상태에서 덱을 바꾸고 재호출하자 새 장으로 DOM이 교체되고 두 번째 `print()`가 호출됐다. 이어 이전 인쇄 종료를 가정한 `afterprint`를 보내자 새 작업의 `printHost`가 비워지고 `printJob`도 `null`이 됐다.
- **근거 [추정]:** 실제 사용자가 인쇄 창이 진행 중일 때 앱으로 돌아와 버튼을 누를 수 있는지, 늦은 종료 이벤트가 겹치는지는 브라우저별로 미확인이다. 대역 시험은 해당 이벤트 순서에서의 코드 동작을 확인한 것이며 Safari·Firefox의 실제 결함을 확정한 것은 아니다.
- **변경과의 관계:** 같은 준비 중 차단·무조건 이전 작업 정리·반환 직후 버튼 잠금 해제 구조가 `main`의 `printPdf`에도 있다. **5차 단순화로 새로 생긴 회귀는 아니다.** 요청서의 “신호가 없으면 다음 인쇄 때 정리” 정책은 보존됐지만, “신호 없이 끝난 작업”과 “아직 진행 중인 작업”은 구분하지 못한다.
- **수정 제안:** 비동기 인쇄를 지원 범위로 삼는다면 인쇄 종료까지 작업 잠금과 DOM·제목을 유지한다. 종료 신호 누락 복구는 사용자가 이전 창을 닫았음을 확인하는 명시적 복구 동작 등으로 분리하는 방안을 권한다. 작업별 종료 처리기를 두되, 전역 이벤트가 어느 인쇄에 속하는지 자체적으로 식별해 주지는 않으므로 작업 겹침 방지가 우선이다.
- **확인 방법:** 실제 지원 브라우저에서 저장·취소·인쇄 진행 중 앱 복귀·재실행·종료 신호 누락을 확인한다. Chrome에서는 일반 저장·취소 후 버튼이 다시 작동하는지도 함께 본다.

## 확인 결과

### 삭제한 코드의 남은 참조

**[정적 확인]** 추적 파일 전체에 대해 `pdfPanel`, `btnPdf`(따라서 `btnPdfMake`·`btnPdfClose` 포함), `inPdfPages`, `parsePages`, `pagesToText`, `#pdf`를 검색했다. 추가로 `pdfRange`, `pdfPick`, `pdfChips`, `printPdf`, `setPdfBusy`도 검색했다.

- 앱 HTML·JS·CSS, 두 스킬 문서, README, AGENTS.md와 스크립트에는 해당 식별자의 실행·사용 안내 참조가 없다.
- 일치한 파일은 `docs/codex요청_4차수정검토.md`, `docs/codex결과_4차수정검토.md`, `docs/codex요청_5차수정검토.md`다. 과거 동작 기록과 삭제 대상 설명이므로 미제거 코드로 판단하지 않았다. 이 결과 문서에도 검토 대상을 설명하기 위해 이름을 적는다.
- `docs/codex검토_반영내역.md:80–86`에는 과거 [PDF]·[만들기]·쪽 선택 창 설명이 남아 있다. **4차 수정 반영 기록**으로 명시돼 있어 오류로 세지 않았다. AGENTS.md의 v1.5.0·v1.6.0 설명도 버전 이력이다.
- `app/deck-spec.js`에서 두 파서 함수의 선언과 `DeckSpec` 내보내기가 함께 제거됐다. 버전은 `1.7.0`이다.
- 버튼 ID는 HTML의 `btnPrint`와 JS 연결(`app/app.js:1444`)이 일치한다. 패널 열기·설정·Esc 처리에서도 삭제한 패널 접근이 제거됐다.

### 인쇄 작업 관리 — Node 격리 실행

실제 인쇄 함수 블록을 파일에서 읽어 VM으로 실행했다. DOM·Image·글꼴 준비·타이머·`window.print`·이벤트만 대역으로 제공했으며, 브라우저나 외부 프로세스를 실행하지 않았다. 합성 3장 덱을 사용했고 사용자 덱은 읽지 않았다.

| 확인 항목 | 결과 |
| --- | --- |
| 전체 장 준비 | 3장이 원래 순서대로 생성되고 각 `makeSlide` 호출에 `editable:false`, `animate:false`가 전달됨 |
| 준비 중 버튼 잠금 | 글꼴 Promise 대기 중 [인쇄] 비활성화 |
| 준비 중 연속 호출 | 두 번째 호출을 무시하고 인쇄는 한 번만 실행 |
| 비동기 `print()` 반환 | 반환 후에도 쪽과 인쇄용 제목 유지 |
| 지연된 `afterprint` | 쪽 제거, 원래 제목 복원, 이벤트 처리기 제거, 작업 상태 초기화 |
| `print()` 내부의 동기 `afterprint` | 정리 후 버튼 정상 복구 |
| 렌더링 예외 / `print()` 예외 | DOM·제목·작업 상태·버튼 복구 및 오류 안내 |
| 3초 제한 초과 | 대역 타이머의 3000ms 설정 확인 후 콜백을 실행하니 경고와 함께 인쇄, 종료 시 경고 정리 |
| 종료 신호 없는 이전 작업 복구 | 다음 호출 때 이전 작업을 정리하고 새 인쇄 진행. 단, 이전 인쇄가 실제로 종료됐다는 전제가 필요함(문제 1) |
| 파일 이름 | 발표 폴더 이름 사용, 폴더 정보가 없으면 `Any-Slide`; 쪽 번호 접미사 없음 |
| 확인용 해시 | `#print`·`#s=3&print`는 준비 함수 실행, 이전 `#pdf`는 실행하지 않음 |

`node --check app/app.js`, `node --check app/deck-spec.js`가 통과했다. Node에서 기본 덱을 생성하고 `sanitize`로 다시 읽어 13장 유지도 확인했다. 이는 화면 배치·PDF 쪽 나눔·배경 인쇄의 실증 시험은 아니다.

### 문서와 실제 동작

- **[정적 확인]** README(`app/README.md:32`), 버튼 설명(`app/Any-Slide.html:30`), 두 스킬 문서(`:90`)가 [인쇄] → 전체 장 준비 → 인쇄 창에서 PDF 대상·일부 페이지 선택 순서로 일치한다. 일부 페이지 선택은 브라우저에 맡기고 앱에서 범위를 해석하는 코드는 없다.
- 두 스킬 문서는 바이트 단위로 동일하다. AGENTS.md의 버전 이력도 1.7.0 변경과 맞는다.
- 인쇄용 페이지 CSS와 `@media print`는 이번 변경에서 동작 변경이 없고, 쪽 선택 패널 전용 CSS만 제거됐다. `#print`는 인쇄용 DOM을 준비할 뿐 자동으로 인쇄 창을 열지 않는다(`app/app.js:1479–1483`).
- “준비하는 동안 [인쇄]가 잠긴다”는 README 설명은 코드와 정확히 맞는다. 인쇄 완료까지 잠근다는 뜻으로 확대 해석하면 안 된다(문제 1).
- 3초 초과 경고와 배경·쪽 크기 설정은 유지됐다. README는 Chrome 외 브라우저를 미확인으로 명시한다. 요청서의 Chrome PDF 33쪽·기본 덱 캡처 동일 보고는 선행 작업자의 결과이며, 이번에 재검증한 것으로 취급하지 않았다.
- 코드 주석(`app/app.js:1225`)의 “인쇄 창 설정을 바꾸지 않아도 된다”는 표현은 README의 브라우저 확인 범위보다 단정적이다. 낮은 우선순위로 “CSS에서 기본값을 지정한다” 정도로 맞추면 좋다. 실제 인쇄 설정 적용 여부는 이번 방식으로 검증할 수 없다.

## 의견 (우선순위 순서)

1. **5차 변경 자체는 새 결함 발견 없이 검토를 마쳤다.** 쪽 선택 UI·파서·스타일·이벤트 제거가 일관되고, 4차 반영의 준비 중 잠금과 인쇄 종료 후 정리 동작도 유지된다.
2. **비동기 인쇄 중 재진입 위험 1건은 별도로 판단한다.** 기존 구조의 잔여 위험이므로 이번 단순화의 회귀와 구분한다. Safari·Firefox까지 지원하려면 실제 이벤트 순서 검증과 작업 수명 보완을 우선한다.
3. **과거 검토 문서는 이력으로 보존한다.** 현재 실행 참조와 과거 설명을 구분하면 된다. 필요하면 반영내역에 5차 단순화 항목을 추가하고, 인쇄 설정 주석의 표현만 실제 확인 범위에 맞춘다.

검토 결과 문서만 저장했다. 소스·사용자 자료 수정, Chrome 실행, 텔레그램 등 외부 전송, 커밋은 하지 않았다.
