## 문제 목록

### 1. 높음 — 미리보기용 HTML에서 덱의 `</script>`가 삽입 스크립트를 종료함

- **위치:** `.claude/skills/slide-deck/scripts/preview-deck.mjs:25–27`.
- **증상:** JSON을 두 번 stringify하더라도 HTML의 script 종료 태그는 이스케이프되지 않는다. 코드 슬라이드에 종료 태그가 있는 정상 자료도 미리보기 초기화를 깨뜨릴 수 있고, 조작된 덱은 임의의 script 태그를 삽입할 수 있다.
- **근거:** [실행 확인 — 격리: 생성 문자열] body에 `</script><script>globalThis.__reviewMarker=1</script>`을 넣고 실제 스크립트의 삽입 표현식을 평가했다. 결과 HTML에 이 태그들이 그대로 남았다. [정적 확인] 이 HTML을 브라우저에 열면 script 문자열의 따옴표와 관계없이 첫 종료 태그가 삽입 스크립트를 끝내는 구조다. 브라우저에서 marker가 실행되는 장면은 확인하지 않았다.
- **범위:** 앱 본체의 sanitize·runsToHTML을 통한 일반 덱 불러오기에서는 같은 문자열이 이스케이프됐다. 이번 문제는 미리보기 스크립트가 검증·렌더링 전에 원문을 HTML script에 넣는 별도 경로다. 임의 OS 명령 실행까지 확인한 것은 아니다.
- **수정 제안:** HTML에 삽입하는 JSON 문자열에서 최소한 `<`를 `\u003c`로 바꾸거나, 스크립트 종료 태그가 만들어지지 않는 데이터 전달 방식을 사용한다. 미리보기 전에 같은 sanitize 검증도 적용한다. `</script>`를 담은 코드·일반 텍스트를 포함해 확인한다.

### 2. 중간 — 이모지 뒤의 선택 위치와 서식 적용 인덱스가 달라 예외 발생

- **위치:** `app/app.js:149–183`, `app/app.js:478–489`.
- **증상:** DOM 선택 오프셋과 items.total은 UTF-16 길이인데, applyFormat은 `for...of`로 코드 포인트 단위의 chars 배열을 만든다. 서로 다른 단위의 인덱스를 그대로 사용한다.
- **재현:** [실행 확인 — 격리] 텍스트 노드 `😀A`에서 오프셋 0~3을 선택하고 applyFormat(el, 'b')를 호출했다. chars는 2개인데 e는 3이어서 `TypeError: Cannot set properties of undefined (setting 'b')`가 발생했다. 이모지 뒤 일부 문자만 고르면 다른 범위에 적용되거나 적용되지 않을 수도 있다.
- **수정 제안:** DOM 오프셋과 서식 적용·복원에 같은 인덱스 체계를 사용한다. UTF-16 인덱스를 유지하거나 코드 포인트/문자소 인덱스와의 변환표를 둔다. 단순히 배열 접근에 조건문만 추가하면 잘못된 선택 범위는 남는다. 한글·이모지·조합형 이모지를 섞어 확인한다.

### 3. 중간 — 표 셀의 역슬래시와 파이프가 왕복 후 다른 열로 분리됨

- **위치:** `app/deck-spec.js:241–258`, `app/deck-spec.js:263–278`, `app/app.js:430–436`.
- **증상:** tableToString은 파이프 바로 앞 문자만 보고 이스케이프 여부를 판단한다. 그런데 runsToMarkup이 역슬래시를 이중화하므로, 바로 앞에 역슬래시가 있어도 파이프 자체는 실제 구분자가 될 수 있다.
- **재현:** [실행 확인 — 격리] 한 셀의 실제 글자를 `a\|b`로 두었다. runsToMarkup → tableToString → parseTable을 통과하면 원래 2개 셀인 `["a\\|b", "옆칸"]`이 3개 셀로 바뀌어 첫 셀은 `a\`, 둘째는 `b`, 셋째는 `옆칸`으로 표시되는 데이터가 됐다. 입력 후 썸네일 갱신·재렌더링·다시 불러오기에서 열 구조가 달라질 수 있다.
- **수정 제안:** 바로 앞 문자 대신 연속 역슬래시 수의 홀짝을 기준으로 파이프를 처리하고, 마크업·표 두 계층의 이스케이프 규칙을 명시한다. 장기적으로는 표를 셀 배열로 저장하고 문자열 표기를 입출력 단계에 한정하는 편이 안전하다.

### 4. 중간 — 서식 있는 텍스트의 끝 개행과 블록 경계가 보존되지 않는 경우

- **위치:** `app/app.js:98–101`, `app/app.js:119–129`, `app/app.js:439–444`.
- **증상:** markupToHTML은 마크업 원문이 개행으로 끝날 때만 자리 채움 BR을 추가하지만, domItems는 각 블록의 마지막 BR을 무조건 자리 채움으로 제거한다. 끝 개행이 서식 닫기 표기 안에 있으면 규칙이 맞지 않는다.
- **재현 1:** [실행 확인 — 격리] `**A\n**`는 `<b>A<br></b>`로 생성된다. 이 DOM을 elToMarkup으로 읽으면 `**A**`가 되어 개행이 사라졌다. 실제 생성된 태그 구조를 대역 DOM으로 구성해 확인했다.
- **재현 2:** [실행 확인 — 격리] `<div>첫줄</div>뒤` 형태의 DOM을 읽으면 `첫줄뒤`가 된다. domItems는 블록 앞의 경계만 넣고 블록 뒤의 일반 텍스트 경계는 넣지 않는다. 실제 contenteditable 조작으로 이 DOM이 만들어지는 경로와 브라우저별 Enter 표현은 미확인이다.
- **잔여 항목:** plain code/num은 여전히 `innerText.replace(/\n$/, '')`를 사용한다(`app.js:442`).
- **수정 제안:** 표시용 자리 채움 노드와 의미 있는 개행을 명확하게 구분한다. 끝 개행 여부는 원시 마크업 끝이 아니라 파싱한 텍스트 기준으로 판단하고, 블록 전후 줄 경계를 모두 정의한다. 서식 마지막 줄·빈 줄 여러 개·Enter/Shift+Enter·붙여넣기의 왕복을 검사한다.

### 5. 중간 — 글자 크기 A+/A−가 최초 상태를 캡처해 연속 적용되지 않음

- **위치:** `app/app.js:505–520`, `app/app.js:687–696`.
- **증상:** renderCtx에서 k를 한 번 읽어 버튼 콜백에 캡처한다. setBoxStyle은 실제 스타일을 바꾸지만 도구 줄은 다시 그리지 않아 다음 클릭도 같은 k를 쓴다. 백분율과 정렬/행간 버튼의 선택 표시도 이전 값으로 남는다.
- **재현:** [실행 확인 — 격리] 기본 100%에서 실제 renderCtx가 만든 A+ 버튼을 두 번 실행했다. 결과는 120%가 아니라 110%였으며 도구 줄 표시는 100% 그대로였다.
- **수정 제안:** 클릭 시점에 boxStyleOf(el)로 현재 값을 읽는다. 편집 DOM과 선택을 보존하면서 도구 줄의 숫자·활성 상태만 갱신한다. 전체 도구 줄 재생성을 택하면 버튼 포커스·범위 선택도 복원해야 한다.

### 6. 중간 — 기본 가운데 정렬인 칸의 왼쪽 정렬을 저장하지 못함

- **위치:** `app/app.js:216–218`, `app/app.js:505–516`, `app/app.js:693–694`; `app/deck-spec.js`의 statement/steps 정렬 정의.
- **증상:** 왼쪽 정렬 버튼은 align='left' 대신 null을 저장한다. 이는 기본값으로 복귀한다는 뜻이어서, 템플릿 기본 정렬이 center인 칸에는 잘못 적용된다.
- **재현:** [실행 확인 — 격리] statement의 quote에 왼쪽 정렬 버튼과 같은 `setBoxStyle(el, 'align', null)`을 적용했다. 저장된 styles에 left가 없고, 다시 slideHTML을 생성하면 `text-align:center`였다. 즉시 DOM에서는 왼쪽처럼 보일 수 있어도 슬라이드를 다시 열면 가운데로 돌아간다.
- **수정 제안:** 명시적인 왼쪽 선택은 `align:'left'`로 저장한다. ‘템플릿 기본값’으로 돌아가는 동작을 별도 제공한다. 버튼의 on 상태도 템플릿의 실제 기본 정렬을 반영한다.

### 7. 중간 — 키보드로 글자 도구에 접근하면 도구 줄이 사라짐

- **위치:** `app/app.js:461–471`, `app/app.js:651–655`, `app/app.js:665–672`.
- **상태:** [정적 확인], 실제 Tab 조작은 [추정].

## 요청 영역별 추가 확인

### 덱 검증과 앱 본체 보안

- [실행 확인 — 격리] 기본 13종 덱은 키 순서를 제외한 구조 비교에서 sanitize 왕복이 일치했고, 모든 형태의 slideHTML 생성에 성공했다. 이는 실제 화면의 시각 검증을 뜻하지 않는다.
- duration=100 → 1, cards count=99 → 4, style scale/lh=99 → 2/2.4, rot=999 → 180으로 제한됐다. 잘못된 align은 제거되고 flip의 문자열 'true'는 true로 취급되지 않았다. 잘못된 좌표는 기본값으로 바뀌었다.
- 외부/인코딩 상위 경로 img는 허용 목록에서 제외됐다. 일반 텍스트 `<img ...>`는 이스케이프됐고, styles/좌표의 속성 삽입 문자열도 생성 HTML 속성으로 남지 않았다. 앱 본체에서 이번 입력들을 이용한 XSS 경로는 발견하지 못했다. 드래그로 외부 HTML을 contenteditable에 넣는 경로는 실기 미확인이다.
- 예전 anim:false는 textAnim:none, imgAnim:false, float:false로 옮겨진다. 장 전환은 새 설정의 기본 fade로 남는다. 기존 ‘애니메이션 끄기’ 의도를 장 전환까지 이어갈지는 호환 정책으로 명확히 할 부분이다.
- 글자 6000자가 잘리지 않고 보존됐고, 실제 addSlide/addSticker 경로는 이미 300장/100개일 때 더 추가하지 않았다. 이전의 ‘앱에서는 만들 수 있지만 다시 못 읽는 상한’ 문제는 이 경로에서 수정됐다.
- 새 스타일·표기·변형의 모든 조합을 전수 검증하지는 않았다. 파일 크기와 표 행/열 개수는 별도 제한이 없으므로 매우 큰 입력의 자원 사용은 추가로 측정하는 편이 좋다.

### 장 전환과 발표

- [정적 확인] 전환 시 이전 장을 inert로 두고, 빠른 다음 이동 때 기존 tr-out을 먼저 제거한다. 지연 제거 콜백도 각 prev 객체를 캡처하므로 타이머가 새 장을 잘못 지우는 경로는 발견하지 못했다. 이를 브라우저 연속 탐색으로 검증하지는 못했다.
- fit의 transform:scale과 전환의 개별 translate/scale 속성을 분리한 것은 같은 transform 값을 덮어쓰던 위험을 줄인다. 창 크기 변경 시 남아 있는 장을 모두 다시 맞춘다. 실제 배율과 전환 시작/종료 프레임의 시각적 일치는 미확인이다.
- 전환 중 이전 장의 편집은 inert로 막지만, 새 장의 편집은 가능하다. 포커스·한글 조합 중 빠른 전환·입력·도구 클릭은 실기 검증이 필요하다.
- 삭제·초기화는 force=true로 이동하여 이전 보고서의 같은 인덱스 조기 반환 회귀를 피한다. 썸네일 활성화 후 포커스 복원도 추가돼 있다.
- 등장 효과는 textAnim/imgAnim/float 경로가 분리돼 있고 reduced-motion 규칙도 유지된다. redraw는 의도적으로 still로 그려 해당 DOM의 등장·둥실둥실을 꺼 둔다. 편집 중 옵션을 바꿨는데 움직임이 즉시 보이지 않는 경우의 사용 정책을 설명하면 좋다.

### 스티커 변형

- [실행 확인 — 격리] 앞으로 이동 후 sel이 함께 증가하고 선택한 src가 유지됐다. 회전 30도인 손잡이를 같은 좌표로 움직이는 입력에서는 30도를 유지했다. Shift의 15도 반올림 분기도 있다.
- [정적 확인] 리사이즈는 회전된 축을 직접 계산하는 대신 중심과 포인터 사이 거리의 비율로 크기를 바꾼다. 네 모서리 모두 같은 동작이며 반대편 모서리를 고정하는 방식은 아니다. 제안한 상호작용과 맞는지 사용자 경험 확인이 필요하다.
- placeSticker를 리사이즈 뒤에도 호출해 이전의 축소 후 위치 무제한 경로는 보완했다. 다만 offsetHeight를 새 너비를 쓰기 전에 읽으므로 극단적인 리사이즈에서 높이 범위가 한 이벤트 늦을 수 있다. 회전된 시각 경계나 투명 PNG의 실제 픽셀까지 보장하는 것도 아니다. 실제 사라짐은 재현하지 않아 [추정]으로 남긴다.
- sanitize의 y 제한은 여전히 w/2이고, placeSticker는 실제 offsetHeight/2를 쓴다. 비정사각 에셋을 경계에 놓으면 다시 불러올 때 y가 약간 바뀔 수 있다. 장기적으로 좌표 정규화 규칙을 한 곳에서 공유하는 편이 좋다.

### 자동 맞춤·상황별 도구 줄

- [실행 확인 — 격리] 높이에 반응하는 대역에서 grow를 두 번 실행해도 같은 최종 크기였고 누적 확대하지 않았다. 매번 기본 크기로 리셋하고 0.05씩 제한하는 구조라 현재 고정된 grow 값에서 무한 반복 경로는 발견하지 못했다.
- [실행 확인 — 격리] offsetParent=null인 숨겨진 상자는 기존 인라인 크기를 유지했다. 편집 복귀와 loadingdone에 썸네일 맞춤 경로도 있어 이전 숨김 측정 문제를 보완했다.
- offsetHeight를 사용해 자신의 등장 transform과 조상의 썸네일 scale에 영향을 덜 받도록 바꿨다. center stack은 고정 부모 높이 대신 자식 offsetTop/offsetHeight 차이를 사용한다. 실제 Chrome의 줄바꿈·서체·표 셀 패딩에 대한 측정은 미완료다.
- 입력 시 해당 box만 맞추고 편집 DOM을 매번 교체하지 않는 방향은 적절하다. 그러나 서식 적용은 innerHTML을 재작성하므로 기본 Undo 기록·선택 방향·한글 조합 도중 버튼 클릭에 대한 실기 검증이 필요하다. 조합 키 단축키는 막지만 포인터 서식 적용에는 별도의 조합 상태 검사가 없다. 실제 조합 손실을 확인한 것은 아니다.
- 도구 줄 내용이 바뀌어 줄 수가 달라질 때 wrap 높이가 달라질 수 있는데 fit은 window resize에 연결돼 있다. 작은 창에서 도구 줄 변경 후 잘림이 있는지는 미확인이다. 컨테이너 크기 관찰을 고려할 수 있다.

### 스킬 문서와 검사 스크립트

- 사전 조사 → 구성/필요 그림 제안 → 수락한 그림 생성 → 덱 작성 → 검사/미리보기의 순서가 명시돼 있고, AGENTS.md에도 같은 방침이 들어갔다. 두 스킬 사본의 내용도 같았다. 이번 작업은 덱 제작이 아니므로 사전 조사나 이미지 생성 흐름을 실행하지 않았다.
- 새 7종을 포함한 13종과 settings/styles/count/rot/flip의 사용법은 문서에 반영됐다. 스킬은 image의 허용 경로를 스티커 표 목록으로 설명하지만 실제 allowedSrc는 고정 템플릿 이미지(char-hands, props-corner 등)도 포함한다. 문서의 목록을 ‘권장 선택지’와 ‘실제 허용 집합’으로 구분하면 혼동이 줄어든다.
- check-deck는 같은 sanitize를 사용하고 넘침·빈 공간 경고를 제공한다. 다만 표 경로는 table의 styles.scale/lh를 반영하지 않고 36px/1.4를 고정한다(`check-deck.mjs:72–75`). 사용자가 표 서식을 바꾼 덱의 경고는 실제 앱과 달라질 수 있다. 추정 검사라는 한계와 별개로 이 두 설정은 계산에 포함하는 것이 좋다.
- 미리보기 스크립트는 각 장을 찍을 때마다 Chrome을 실행한다. 현재 환경에서는 충돌 알림을 반복시킬 수 있어 실행하지 않았다. 애니메이션도 강제로 끄므로 해당 PNG만으로 장 전환을 검증할 수는 없다.

## Chrome 실행과 중단 기록

요청의 ‘가능하면 Chrome’에 따라 검토 초기에 임시 프로필과 `--headless=new --dump-dom about:blank`로 한 번 실행했으나 종료 코드 134로 실패했다. 앱 파일을 로드하기 전 단계였다. macOS 진단 파일 `Google Chrome-2026-10-21-220838.ips`에는 EXC_CRASH/SIGABRT, Abort trap:6과 `_RegisterApplication`/`TransformProcessType`/`ChromeMain` 스택이 기록돼 있었다. macOS 앱 등록 경로에서 중단된 정황이며 최종 환경 원인은 단정하지 않는다.

이후 사용자가 반복되는 Chrome 비정상 종료 알림을 중단해 달라고 요청했다. **그 요청 이후 Chrome 재실행과 preview-deck 실행을 하지 않았다.** 시스템·보안·충돌 알림 설정도 바꾸지 않았다. 실제 브라우저 캡처, 한국어 입력기, 전체 화면, 포인터 캡처·터치, 전환 속도/배율, 폰트 로드 타이밍 검증은 미완료다.

## 의견: 우선순위 순서

1. **미리보기 HTML의 script 삽입 경로를 먼저 수정한다.** 코드 예제에 종료 태그가 있는 정상 덱과 조작된 덱 모두 안전하게 미리보기해야 한다.
2. **서식 왕복의 데이터 보존을 고정한다.** UTF-16 선택, 끝 개행, 연속 역슬래시+파이프를 재현 사례로 두고 parse/serialize/DOM 읽기의 계약을 맞춘다. 특히 표 셀 데이터와 표시용 마크업의 계층을 분리한다.
3. **도구 줄의 상태와 포커스를 정리한다.** 현재값을 읽는 크기 버튼, 명시적인 왼쪽 정렬, 도구 줄로 포커스가 이동해도 유지되는 편집 대상·선택 범위, 스티커 선택 후 키보드 이동 경로를 함께 보완한다.
4. **브라우저 검증은 정상 실행 가능한 환경에서 수행한다.** 현재 환경의 Chrome은 재시도하지 않는다. 가능한 환경에서 한글 조합/붙여넣기/Undo/Tab, 전환 중 편집·빠른 이동, 회전 리사이즈, 썸네일·폰트 로드 전후를 묶어 확인한다.
5. **검사와 스키마를 더 공유한다.** 표 서식의 경고 계산, 허용 이미지 목록, 비정사각 스티커 위치 제한을 실제 렌더링 규칙과 맞춘다. 큰 표·큰 덱의 비용은 측정 후 제한이나 부분 갱신을 정한다.
