## 문제 목록

### 1. 높음 — 끌기 중 슬라이드를 바꾸면 다음 장에 이전 개체의 배치가 저장됨

- **위치:** `app/app.js:715–781`, `app/app.js:802–811`, `app/app.js:637–643`, `app/app.js:452–459`.
- **증상:** 끌기는 window 이벤트로 계속되지만 대상 슬라이드 참조를 보관하지 않는다. 종료 시 setLayout은 그때의 `deck.slides[cur]`에 저장한다. 장 이동 시 진행 중인 끌기를 종료하는 경로도 없다.
- **근거:** [실행 확인 — 격리] 표지 title을 x=160/y=235에서 x=260/y=335로 끄는 이벤트를 전달했다. pointerup 전에 실제 `go(1, true)`로 본문 장에 이동하고 손을 뗐다. 결과는 표지 layout=null, 본문 layout.title={x:260,y:335}였다. 표지 이동은 보존되지 않고 다음 장의 제목 배치가 바뀌었다.
- **실제 조작 조건:** 포인터를 누른 상태에서 PageDown 등 장 이동 키를 누르는 경로가 가능하다. 실제 키보드+포인터 동시 조작은 실행하지 않았으며, 격리 검사에서는 동일한 장 이동 함수와 종료 핸들러를 호출했다.
- **수정 제안:** 끌기 시작 때 대상 slide 객체·개체 id·포인터 id를 함께 고정한다. go/형태 변경/삭제/모드 전환 전에 진행 중인 끌기를 커밋 또는 취소하고 리스너를 정리한다. 종료 콜백이 임의의 현재 cur에 쓰지 않게 한다.

### 2. 중간 — 그림 개체의 키보드 세로 이동은 실제 높이를 고려하지 않아 완전히 화면 밖으로 나감

- **위치:** `app/app.js:862–868`, `app/app.js:1166–1169`; `app/deck-spec.js:61`의 hero 등 h가 없는 img 정의.
- **증상:** nudgeObj는 `(o.h || 0)`으로 y 범위를 계산한다. 기본 img에는 h가 없으므로 y=0~1080을 허용하고, 아래 끝에서는 그림의 위쪽이 슬라이드 바닥과 같아진다.
- **근거:** [실행 확인 — 격리] 표지 hero를 y=1070에 놓고 실제 높이가 804px인 노드 대역에서 nudgeObj(0,50)를 호출했다. 결과 y=1080이었다. 그림 전체가 슬라이드 아래에 있는 좌표다. `.slide`는 overflow:hidden이다(`style.css:81`).
- **영향:** 마우스 끌기의 중심 제한과 키보드 이동 제한이 다르다. 선택을 잃으면 그림을 다시 클릭할 수 없고 전체 원래 배치 복구 등에 의존한다.
- **수정 제안:** img의 실제 높이 또는 검증된 종횡비를 사용하고, 이동·리사이즈·키보드·불러오기에서 같은 가시성 규칙을 공유한다. 회전된 그림과 이미지 로드 전 상태도 함께 처리한다.

### 3. 중간 — 상자 리사이즈의 상한이 없어 앱이 저장한 배치가 다시 열 때 달라짐

- **위치:** `app/app.js:749–752`, `app/app.js:809–811`; `app/deck-spec.js:422–425`.
- **증상:** 비율 고정 그림과 달리 일반 상자 리사이즈는 최소값만 둔다. 저장 때 큰 w/h가 그대로 들어가지만 sanitize는 w≤3840, h≤2160으로 줄인다.
- **근거:** [실행 확인 — 격리] 표지 제목의 동쪽 손잡이를 Alt를 누른 채 5000px 이동시키는 이벤트를 전달했다. 실제 저장 layout.title.w는 5800이었다. 같은 덱을 JSON 왕복하여 sanitize하면 w=3840이 됐다. 배치 내용이 잘린다는 알림은 없다.
- **수정 제안:** 조작·커밋·sanitize가 같은 최소/최대값을 사용하게 한다. 더 큰 개체를 허용할 의도라면 스키마 범위를 맞춘다. 크기 제한 뒤 위치와 스냅 결과도 다시 검증한다.

### 4. 중간 — 묶음 상자를 작게 줄이면 내부 글자 폭이 음수가 되거나 바탕 밖으로 나감

- **위치:** `app/app.js:749`, `app/app.js:791–796`; `app/deck-spec.js:213–221`, `app/deck-spec.js:424–425`.
- **증상:** 외부 상자는 폭60/높이40까지 줄일 수 있지만 내부 패딩과 제목 위치는 고정이다. cardInner의 폭은 w-100 또는 w-80이라 음수가 될 수 있다. bubble/code의 최소 내부 폭100도 외부 폭60에 들어가지 않는다.
- **근거:** [실행 확인 — 격리] compare 상자 w=60/h=40의 cardInner 결과는 제목·본문 폭 -40, 본문 y=190/h=60이었다. 실제 slideHTML에도 `width:-40px`가 생성됐다. sanitize는 더 작은 w/h=20도 허용한다. [정적 확인] 이는 유효한 CSS 폭이 아니며, 작은 바탕에 내용이 맞는다는 조건도 깨진다. 정확한 브라우저 표시 모양은 미확인이다.
- **수정 제안:** 종류별 최소 크기를 내부 배치와 함께 정의하거나 내부 배치 자체를 비례 조정한다. 계산 결과의 w/h뿐 아니라 x+w≤외부 w, y+h≤외부 h도 확인한다. inspector와 checker가 같은 배치 함수를 쓰더라도 잘못된 치수를 함께 공유할 수 있다는 점에 주의한다.

### 5. 중간 — 현재 자동 정렬과 같은 값을 선택하면 수동 선택이 저장되지 않음

- **위치:** `app/app.js:488–492`, `app/app.js:967–976`; `app/deck-spec.js:258–261`.
- **증상:** 정렬 버튼은 현재 align0와 같은 선택을 null로 저장한다. 자동 정렬 칸의 align0는 입력에 따라 바뀌므로 사용자가 명시적으로 가운데/왼쪽을 골랐어도 다음 입력이 그 선택을 바꾼다.
- **근거:** [실행 확인 — 격리] 짧은 compare 내용에서 실제 도구 줄의 ‘가운데 정렬’ 버튼을 실행했다. styles는 null이었다. 그 뒤 15자의 내용을 입력해 commitText를 호출하자 text-align은 left가 됐다. ‘사용자가 정렬을 정하면 그 값이 우선’이라는 설명과 다르다.
- **수정 제안:** 자동 정렬 대상에서는 정렬 버튼의 명시적 선택을 항상 저장한다. 자동으로 되돌리기는 별도 ‘자동’ 버튼으로 제공한다. 일반 입력에서 14→15자 또는 2→3줄에 따라 자동값이 바뀌는 동작 자체는 현재 규칙대로이며, 이번 지적은 사용자가 고정하려고 선택한 경우다.

### 6. 중간 — 다른 포인터의 이벤트도 진행 중인 끌기를 이동·종료시킴

- **위치:** `app/app.js:715–781`.
- **증상:** 시작 이벤트의 pointerId를 보관·검사하지 않는다. window의 모든 pointermove/up/cancel을 하나의 끌기로 처리하므로 다른 터치나 펜 입력이 선택 개체를 움직이거나 먼저 종료할 수 있다.
- **근거:** [실행 확인 — 격리] pointerId=1로 시작하고, pointerId=2의 이동(+200,+200)과 pointerup을 전달했다. title은 x=360/y=435로 저장됐고 원래 끌기의 move 리스너도 제거됐다.
- **추가 위험:** [정적 확인/추정] 노드 교체를 견디도록 리스너를 window에 두었지만 포인터 캡처와 blur 등 종료 복구가 없다. 창 밖에서 손을 뗐을 때 남은 리스너의 실제 동작은 확인하지 못했다.
- **수정 제안:** 시작 pointerId 외의 이벤트는 무시한다. 교체되지 않는 stage/host에 캡처를 설정하는 방식 등을 검토하고, 종료·취소·캡처 상실·장 이동에서 한 번만 정리되는 공통 종료 경로를 둔다.

## 중점 항목별 추가 확인

### 회전·맞춤·개체 교체

- [실행 확인 — 격리] 90도 회전한 400×200 상자의 동쪽 손잡이를 회전 축 방향으로 100px 늘리면 x=450/y=350/w=500/h=200이 됐다. 고정해야 하는 반대편의 세계 좌표는 유지되는 계산이다. bboxOf도 같은 상자의 l=600/r=800/t=200/b=600을 반환했다. 임의 각도·모든 손잡이를 전수 검사한 것은 아니다.
- nearest는 값151과 기준선160에서 d=9를 반환했다. 경계10px의 조건과 Alt로 맞춤을 끄는 분기는 소스에 있다. 실제 보조선의 시각적 일치는 미확인이다.
- [정적 확인] 회전하지 않은 일반 상자 크기 조절에만 변 맞춤을 적용하고, uniform 이미지·스티커 크기 조절 및 회전한 상자 크기 조절에는 적용하지 않는다. 이 경우에도 맞춤 끄기 안내가 뜬다. 지원 범위로 의도한 것인지 안내를 맞추면 좋다.
- makeObjNode를 이용한 교체 뒤 t.el을 새 노드로 바꾸고 sel/still을 다시 붙이며, 이벤트는 window에 있어 제거된 노드의 리스너에만 의존하지 않는다. [실행 확인 — 격리] 노드 교체 대역에서도 두 번째 이벤트와 종료까지 이어졌고 새 노드에 sel이 유지됐다. 실제 makeObjNode의 브라우저 파싱과 터치 동작을 검증한 것은 아니다.
- 스냅 후 중심 제한이 다시 좌표를 바꿀 수 있지만 그린 보조선은 이전 guides 값을 사용한다. 큰 회전 개체를 화면 경계에 두었을 때 보조선과 최종 위치가 다를 가능성은 [추정]이며 별도 실기 확인이 필요하다.

### layout 검증과 호환

- [실행 확인 — 격리] 기본 덱 13종은 키 순서를 제외한 구조 비교에서 sanitize 왕복이 같았고, 모두 placedObjects와 slideHTML을 생성했다. layout이 없는 예전 덱은 기본 위치를 사용한다. anim:false의 이전 설정 변환도 유지돼 있다.
- 허용되지 않은 layout id는 제거되고, 비유한 숫자·문자열 숫자는 배치 필드로 복사되지 않는다. w=-5는20, h=99999는2160, rot=999는180으로 제한됐다. hidden의 문자열 'true'는 true로 취급되지 않았다. 해당 숫자/ID에서 HTML 속성 삽입 경로는 발견하지 못했다.
- [실행 확인 — 격리] count=2인 카드 장의 c4 배치와 hidden은 보존되지만 현재 placedObjects에는 title/c1/c2만 나타났다. 검증에 expandObjects(all=true)를 쓰므로 개수를 다시 늘릴 때 복원할 상태를 보존한다. 개수별 기본 격자는 바뀌므로 일부 카드에만 사용자 배치가 있으면 수 변경 후 겹침이 생길 수 있다. 이를 자동 보정할지 유지할지는 제품 정책으로 정할 부분이다.
- [정적 확인] 형태 변경은 `delete s.layout` 후 다시 그린다(`app.js:1195–1200`). 이전 형태의 같은 id가 새 형태에 섞이는 것은 막는다. 배치를 의도적으로 초기화하는 현재 정책은 스킬 문서에도 적혀 있다.
- 범위 제한은 가시성을 보장하는 제한은 아니다. sanitize는 x=3840/y=2160 같은 화면 밖 위치도 허용한다. 외부 덱의 화면 밖 배치에 경고를 주거나 전체 원래 배치 복구를 안내하면 좋다. hidden 개체 복구와 배치 전체 reset 경로는 마련돼 있다.

### 글자 편집·선택·키보드

- [정적 확인] `.t[contenteditable]`를 누르면 pointerdown이 끌기를 시작하지 않고 반환한다. `.eg` 또는 `.h`를 누르면 releaseFocus 후 끌기를 시작한다. 표 셀·카드 내부 텍스트도 같은 편집 분기를 탄다.
- 포커스가 글자에 있을 때 방향키/Delete는 typing 검사에서 반환하므로 개체를 지우거나 움직이는 명령과 분리된다. 조합 중 키도 먼저 반환한다. 개체/스티커를 포인터로 선택할 때는 releaseFocus로 버튼에 남은 포커스를 해제한다.
- 도구 줄 버튼에 키보드 포커스가 있으면 해당 버튼의 키 동작을 우선한다. 선택 개체의 방향키를 어느 컨텍스트까지 허용할지는 명시하면 좋다. 포인터로 선택한 뒤 키보드로 이동하는 경로는 코드상 마련돼 있다.
- 도구 줄 포커스 복원과 lastRange가 추가된 상태다. 다만 회전한 글상자 안의 실제 커서·한글 입력·범위 선택, resize 교체 시 Undo 기록은 이번 격리 실행으로 확정할 수 없다.
- 카드 본문과 표 일반 셀은 autoAlign, 카드 제목과 표 머리 줄은 center를 기본으로 쓴다. `styles[field].align`이 존재하면 렌더링과 입력에서 우선한다. 명시적 자동값 선택이 저장되지 않는 문제는 위 5번과 같다.

### 검사 스크립트

- **layout은 반영된다.** checker가 `textBoxes(slide)`를 호출하고, 이 함수는 `placedObjects`의 실제 w/h 및 hidden을 사용한다(`check-deck.mjs:52–53`, `deck-spec.js:224–237`). 표의 styles.scale/lh도 계산에 반영됐다.
- [실행 확인 — 격리] 같은 본문 150자 덱을 기본 배치로 검사하면 통과했고, layout.main={w:300,h:100}을 추가하면 ‘최소 크기로 줄여도 넘침’ 경고가 나왔다. 기본 13장 덱도 통과했다.
- 회전·x/y로 화면을 벗어나는지, 다른 개체와 겹치는지는 검사하지 않는다. 또한 4번처럼 내부 폭이 음수인 배치를 검사 전에 거부하지 않아 높이 추정이 무의미해질 수 있다. 배치 유효성 검사와 내용량 추정은 구분하여 보완하는 편이 좋다.

### 패널과 정보 표시

- [실행 확인 — 격리] STICKERS는 basic 8개/extra 2개이며 APP_VERSION은 1.2.0이다. [정적 확인] 탭으로 필터링해 표시하고, 이름·여백을 추가했으며 정보 팝업 문자열도 APP_VERSION을 참조한다.
- role=tab은 있지만 aria-selected나 탭 간 방향키 이동은 추가하지 않았다. 정보 팝업의 초점 이동·복귀도 명시적 처리가 없다. 기능 동작과 별도로 접근성 보완 대상으로 두면 좋다.
- 패널 잘림·정보 버튼의 실제 위치·가독성은 화면 검증하지 않았다. Chrome을 실행하지 않는 이번 요청 범위에서 육안 확인을 했다고 주장하지 않는다.

## 의견: 우선순위 순서

1. **끌기의 대상과 수명을 고정한다.** 장 이동 전 끌기 종료와 대상 slide/포인터 id 고정부터 처리한다. 1번·6번은 공통 종료 설계로 함께 해결할 수 있다.
2. **기하 제약을 한 곳으로 모은다.** 실제 이미지 높이, 종류별 최소 크기, 최대 크기, 위치 제한을 마우스·키보드·sanitize가 공유하게 한다. 앱이 저장한 배치가 다시 열려도 같아야 한다.
3. **수동 정렬을 자동 정렬과 구분한다.** 명시적 선택은 유지하고 ‘자동으로’ 복귀를 별도 제공한다. 입력 중 자동 정렬 변경 자체는 현재 사양대로 둔다.
4. **배치 검사를 확장한다.** 음수 내부 폭/높이, 화면 밖 배치, 필요시 겹침을 먼저 검사한 후 글자량 추정을 수행한다. 회전/카드 개수 변경의 경계 사례도 포함한다.
5. **실기 확인은 정상 실행 가능한 별도 환경에서 한다.** 회전한 글자 편집, 그룹 resize의 포인터·초점·Undo, 다중 포인터, 빠른 장 이동, 반응형 패널 배치를 확인한다. 이번 환경에서는 요청대로 Chrome을 실행하지 않았다.
