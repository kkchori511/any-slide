## 새 문제

### N1. 높음 — 같은 인덱스 조기 반환이 삭제·초기화를 막아 화면과 덱이 달라짐

- **위치:** `app/app.js:292`, `app/app.js:471`, `app/app.js:522`.
- **상태:** [실행 확인 — 격리].
- **증상:** `go()`는 현재 번호와 같으면 기존 DOM이 있다는 이유만으로 반환한다. 그 사이 덱이 바뀌었는지는 확인하지 않는다.
- **재현 1:** 기본 덱 첫 장에서 삭제 버튼의 핸들러를 실행했다. 실제 덱은 5장이고 첫 장 type은 body인데, stage는 여전히 cover HTML이고 썸네일도 6개였다. 마지막 장이 아닌 장을 삭제하면 같은 패턴이 된다. 그대로 입력하면 화면에 보이는 이전 장의 필드명으로 실제 다음 장을 수정할 수 있다.
- **재현 2:** 첫 장 제목을 CUSTOM으로 바꿔 렌더한 뒤 초기화했다. 덱 제목은 기본값으로 돌아갔지만 DOM은 같은 객체이고 CUSTOM을 계속 포함했다. 다른 장에서 초기화할 때는 cur를 먼저 0으로 설정하므로 이 조기 반환에 역시 걸린다.
- **수정 제안:** 경계 탐색에서만 동일 장 재생을 막는다. 삭제·초기화처럼 데이터가 바뀌는 경로는 `go(..., true)` 또는 명시적인 stage/썸네일/툴바 재렌더를 사용한다. 선택 상태도 함께 초기화한다.

### N2. 높음 — 읽기 때만 적용하는 제한 때문에 앱이 만든 덱이 다시 열리지 않거나 잘림

- **위치:** `app/app.js:124`, `app/app.js:132`, `app/app.js:141–142`, `app/app.js:300–306`, `app/app.js:366–383`, `app/app.js:462–464`.
- **상태:** [실행 확인 — 격리].
- **증상:** MAX_SLIDES/MAX_STICKERS/MAX_TEXT를 sanitize에서만 적용한다. 입력·추가·복제·저장·내보내기에서는 같은 제한이 없다.
- **재현 1:** 실제 `addSlide()`를 반복해 301장으로 만들고 flushSave했다. 저장에는 301장이 있었지만 `loadDeck()`으로 다시 읽으니 기본 6장이 열렸고 원문은 broken 백업으로 이동했다. 사용자가 정상 UI로 만든 덱을 앱 스스로 읽지 못한다.
- **재현 2:** 제목 5001자를 JSON 왕복해 sanitize하면 5000자만 남고, 스티커 101개는 100개가 된다. 둘 다 잘렸다는 오류나 경고 없이 진행된다. 큰 기존 덱에도 같은 마이그레이션 문제가 있다.
- **수정 제안:** 작성 시점과 저장·불러오기 정책을 일치시킨다. 제한을 넘는 추가/복제/붙여넣기는 작업 전에 알리고 거절하거나 더 큰 덱을 안전하게 지원한다. 기존 내용은 무통지 slice로 버리지 말고 원문 보존·명시적 확인·버전 마이그레이션을 제공한다.

### N3. 중간 — 크기 조절 뒤 좌표를 재제한하지 않아 스티커가 다시 사라짐

- **위치:** `app/app.js:145–146`, `app/app.js:342–348`.
- **상태:** [실행 확인 — 격리], 실제 드래그 실기는 미확인.
- **재현:** 허용되는 상태인 `x=-960, w=1920` 스티커에 크기 조절 포인터 이동을 전달했다. 최종 값은 `x=-960, w=40`이었다. 오른쪽 끝도 -920이어서 슬라이드와 겹치지 않는다. resize 분기에는 위치 제한이 없으며, 줄인 상태가 저장된다.
- **추가 근거:** y 범위는 실제 높이 대신 w/2를 사용한다. `assets/props-row.png`처럼 세로가 짧은 이미지는 y=-w/2에서도 완전히 위로 나갈 수 있다. 숫자 제한만으로 실제 보이는 픽셀의 절반을 보장하지는 못한다.
- **수정 제안:** 리사이즈 종료 시에도 좌표를 재검증한다. 실제 이미지 종횡비로 높이를 계산하거나 고정된 선택 상자를 정의한다. 객체 목록/중앙으로 이동 같은 복구 수단도 있으면 좋다.

### N4. 중간 — 발표 중 숨겨진 썸네일을 fitText하고, 복귀할 때는 다시 맞추지 않음

- **위치:** `app/app.js:234`, `app/app.js:265–280`, `app/app.js:394–400`, `app/app.js:528`, `app/style.css:134`.
- **상태:** [정적 확인], 높이 0을 공급한 경우의 함수 동작은 [실행 확인 — 격리]. 실제 브라우저 화면은 [추정].
- **증상/근거:** 발표 모드에서 #thumbs는 display:none이다. 그런데 go()는 발표 중에도 모든 썸네일을 다시 만들고 fitText(list)를 호출한다. 숨겨진 요소에는 레이아웃 박스가 없어 scrollHeight가 0이 된다. fitText는 먼저 인라인 글꼴 크기를 지우므로 기본 크기·over=false로 남긴다. 편집 복귀의 setMode()는 stage만 다시 만들고 썸네일을 재측정하지 않는다. 글꼴 loadingdone이 발표 중 발생해도 같은 경로가 있다.
- **격리 검사:** 이미 축소된 인라인 24.2px와 over가 있는 텍스트에 scrollHeight=0을 공급하면, fitText 후 인라인 크기가 빈 값이 되고 over도 제거됐다.
- **브라우저 재현 제안:** 긴 제목/본문이 축소된 덱에서 발표 → 다음 장 이동 → Esc → 썸네일과 본문 비교. 현재 장 썸네일을 다시 눌러도 같은 번호라 go가 반환하여 복구하지 못할 수 있다.
- **수정 제안:** 숨겨진 루트는 측정하지 않고 표시된 뒤 다시 맞춘다. 편집 모드 복귀 시 fitText(thumbs) 또는 썸네일 재생성을 수행한다. CSS 박스가 없는 요소의 scrollHeight=0 규칙은 [CSSOM View 명세](https://drafts.csswg.org/cssom-view/#dom-element-scrollheight)에 근거한다.

### N5. 중간 — 복구용 백업 실패를 성공으로 안내

- **위치:** `app/app.js:117–119`, `app/app.js:166`.
- **상태:** [실행 확인 — 격리].
- **재현:** 손상된 원문이 저장돼 있고 추가 setItem은 실패하는 저장소 대역에서 loadDeck을 호출했다. broken 백업은 없는데 loadWarning은 “복구용으로 남겨 두었어요”였다. 원본 키에는 당장 원문이 남지만 이후 저장이 성공하면 정상 덱으로 덮어써질 수 있다. 성공한 일반 저장은 경고도 지운다.
- **수정 제안:** 백업 성공 여부를 추적하고 실패 시 성공을 주장하지 않는다. 원문을 메모리에 보관해 별도 다운로드를 제공하거나, 복구 결정을 하기 전 원본 덮어쓰기를 방지한다. 발표 중에는 #hint가 숨겨지므로 저장 오류를 알릴 별도 상태 영역도 고려한다.

### N6. 낮음 — URL 인코딩으로 assets 내부 경로 제한을 벗어남

- **위치:** `app/app.js:144`.
- **상태:** [실행 확인 — 격리: sanitize 및 표준 URL 해석]. 브라우저 파일 접근은 미확인.
- **재현:** `assets/%2e%2e/index.html`은 정규식 및 includes('..')를 통과한다. 앱의 file URL을 기준으로 `new URL()`로 해석하면 `app/index.html`이 된다. 다른 이미지 경로로도 폴더 경계를 벗어날 수 있다.
- **영향 구분:** 이전의 HTML 속성 주입 재발이나 원격 코드 실행을 확인한 것은 아니다. “assets 폴더 안 파일만 허용”이라는 새 정책을 문자열 검사만으로 보장하지 못하는 문제다.
- **수정 제안:** STICKERS와 허용한 에셋 경로의 명시적 목록을 사용하거나, 기준 URL에 대해 정규화한 뒤 실제 경로와 origin이 assets 하위인지 확인한다. 쿼리·프래그먼트·인코딩 허용 정책도 함께 정한다.

## fitText와 stack 집중 검토

### 종료 조건

- [실행 확인 — 격리] 항상 높이를 초과하는 scrollHeight 대역을 주어도 함수는 종료했다. 기본 44px 텍스트의 최종 크기는 약 24.2px(55%)였고 over=true였다.
- [정적 확인] k를 매번 0.05 줄이고 0.55로 제한하므로 최대 9번 크기를 변경한다. 무한 루프는 발견하지 못했다. 위 검사에서는 종료 조건 재검사와 최종 판정을 포함해 높이를 11번 읽었다.
- data-h는 현재 코드의 양수 상수이며 JSON에서 임의의 data-h를 가져오지 않는다. 최소값 clamp도 있다. 소수점의 미세 오차는 이 검사에서 종료를 막지 않았다.

### 입력 성능과 커서

- [정적 확인] 주석은 “입력 중인 칸만”이라고 하지만 실제로는 boxEl.parentElement, 즉 대체로 현재 slide 전체를 fitText한다(`app.js:304–305`). 본문 입력도 stack의 부모인 slide를 대상으로 한다.
- 글자 크기 초기화 → computed style/scrollHeight 읽기 → 글자 크기 쓰기 → 다시 높이 읽기가 반복되어 동기 레이아웃 계산을 유발할 수 있다. 현재 템플릿은 data-h가 2~3개라 무조건 성능 장애라고 단정할 정도의 규모는 아니다. 실제 입력 지연 시간은 측정하지 못했다.
- 썸네일은 250ms 디바운스가 있지만 이동 때 전체 재생성·측정한다. 300장이라면 600~900개 높이 제한 상자를 한 번에 처리할 수 있다. 큰 덱의 실제 비용은 별도 측정이 필요하다.
- 입력 시 기존 편집 DOM의 fontSize만 바꾸므로 stage 교체로 커서가 초기화되는 구조는 아니다. 다만 모든 입력마다 기본 크기로 돌렸다가 축소하므로 시각적 흔들림과 조합 중 레이아웃 변화는 실기로 확인해야 한다.
- 제안: 한 칸/한 stack만 받는 맞춤 함수를 두고, 필요하면 requestAnimationFrame으로 같은 프레임의 변경을 묶는다. 이분 탐색 최적화는 우선 실제 비용을 측정한 뒤 결정한다.

### 썸네일 배율과 글꼴 로드

- [정적 확인] 썸네일 scale(0.1)은 조상 slide의 CSS transform이다. 글꼴의 CSS px와 레이아웃 높이를 비교하는 방식이므로 **단순히 썸네일이라는 이유로 h에 0.1을 곱할 필요는 없다**. 실제 브라우저에서 동일 내용의 최종 축소율을 비교하지는 못했다.
- 문제는 배율보다 N4의 display:none 측정이다. #s=3&view 시작 뒤나 발표 중 이동 후 편집 복귀도 검증해야 한다.
- [정적 확인] loadingdone 리스너가 host와 thumbs를 다시 맞추므로 늦게 로드된 폰트를 처리하는 경로는 추가됐다(`app.js:528`). 이벤트 등록도 초기 렌더 전이다. 단, 이벤트 당시 숨겨진 썸네일과 복귀 처리는 보완해야 한다.
- 최종 커밋에는 Paperlogy 400/500/600/700/800의 로컬 WOFF2와 @font-face가 추가돼 있다(`style.css:2–6`, `style.css:15`). 기존의 “기준 글꼴 미번들” 상태는 해소됐으며 파일 5개도 모두 존재한다. font-display:block의 초기 표시와 실제 파일 로드 성공, 그 전후 fitText 결과는 브라우저에서 검증하지 못했다.

### 애니메이션 중 높이 측정

- [정적 확인] renderStage는 애니메이션 클래스를 붙이고 DOM에 삽입한 즉시 fitText를 실행한다. 애니메이션 완료 후 재측정은 없다(`app.js:255–260`).
- [추정] 개별 .t 자신의 변환과 달리, stack 안 자식의 fade-up translateY(26px)는 부모의 스크롤 오버플로 측정에 영향을 줄 가능성이 있다. 최종 내용이 540px에 근접할 때 편집 stage는 불필요하게 더 작아지고, 애니메이션 없는 썸네일은 기본 크기를 유지하는 차이가 생길 수 있다. 실제 엔진별 scrollHeight는 확인하지 못했으므로 확정 결함으로 집계하지 않았다. 변환이 스크롤 오버플로에 영향을 줄 수 있다는 근거는 [CSS Transforms 명세](https://drafts.csswg.org/css-transforms-1/#transform-rendering)다.
- 제안: 애니메이션용 바깥 래퍼와 측정용 내부 텍스트를 분리하거나, 변환 없는 측정 상태에서 맞춘 뒤 애니메이션을 시작한다. 경계 높이 내용으로 anim on/off 및 reduced-motion의 축소율을 실제 비교한다.

### 본문 stack 렌더링과 편집

- [정적 확인] stack은 absolute 위치의 부모이고 내부 .t는 relative/flex column이다. body/sub의 개별 data-field와 contenteditable이 유지되어 기존 입력 핸들러로 각각 저장된다. 부모를 통해 묶음 전체를 맞추므로 본문만 줄이고 보조 설명이 남는 방식의 불균형도 피한다.
- 기본 한 줄 본문 44px×1.5=66px 뒤 gap 68px가 붙으므로 보조 설명 시작은 y=318+66+68=452다. 이전 기본 레이아웃의 시작점을 보존한다. 본문이 늘어나면 보조 설명이 아래로 밀린다.
- data-h=540은 스타일의 실제 height/max-height가 아니고 판단용 값이다. 55%에서도 넘치면 빨간 테두리만 나타나며 내용은 다른 칸·얼굴 영역까지 이어질 수 있다. 발표 모드는 .edit가 없어 경고 테두리도 표시되지 않는다. 이는 요청된 “그래도 넘치면 over 표시” 구현과는 맞지만, 발표 전 점검이나 넘침 정책은 추가하는 편이 좋다.
- gap 68은 글자가 축소돼도 그대로다. 줄 높이가 작은 상태에서는 간격 비중이 커지므로 글꼴 축소와 gap 축소를 함께 할지는 디자인 결정 사항이다.

## 의견: 다음 우선순위

1. **N1과 N2부터 수정한다.** 삭제·초기화 후 DOM/덱 일치, 앱이 만든 덱의 무손실 재로딩이 가장 중요하다. 이 두 경로는 작은 회귀 검사로 고정할 가치가 있다.
2. **N3/N4/N5를 보완한다.** 스티커 크기 변경 후 위치 재제한, 편집 복귀 시 썸네일 재측정, 백업 성공 여부에 맞는 복구 안내를 추가한다.
3. **실제 Chrome에서 fitText의 경계 사례를 확인한다.** 같은 긴 덱으로 stage/썸네일/발표, anim on/off, reduced-motion, 글꼴 변경 전후를 비교한다. 한국어 조합 중 입력·삭제·Esc와 긴 stack의 커서 유지도 함께 본다.
4. **데이터 경로 정책과 접근성을 마무리한다.** 인코딩 경로 정규화, 썸네일 포커스 복원, 선택한 스티커의 키보드 이동·크기 조절을 보완한다. 끝 개행 보존은 기존 미수정 항목으로 유지한다.
5. **성능은 측정 결과에 맞춰 개선한다.** 입력 칸만 맞추기부터 적용하고, 큰 덱의 썸네일 전체 재측정 비용을 본 뒤 부분 갱신·캐시를 결정한다.
