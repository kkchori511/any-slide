# 10차 수정 검토 결과 (v1.12.0)

## 요약

- `main`(`b494be2`)과 `line-step`(`7de7965`, 검토 시 HEAD)의 차이를 코드 읽기와 Node 격리 실행으로 검토했다.
- 빈칸의 경계가 서식 조각과 혼동돼 한 답이 여러 단계로 나뉘고, 붙어 있는 두 빈칸은 저장 시 하나로 합쳐지는 문제를 재현했다.
- 답 숨김의 접근성 처리 누락과 편집용 빈칸 바탕이 출력 DOM에도 적용되는 범위 문제를 확인했다. 실제 화면 읽기·인쇄 결과는 이번에 시험하지 않았다.
- 일반 표기 왕복·단계 순서·앞뒤 이동·장 단위 모드·숨긴 개체 제외는 통과했고, 기본 13장의 생성 HTML은 `main`과 같았다.
- 결과 문서 외 소스·사용자 덱·생성기록·바탕화면은 수정하지 않았다. Chrome·미리 보기·텔레그램 실행과 외부 전송도 하지 않았다.

## 문제 목록

### 1. [중간] 빈칸 경계를 서식 조각으로 처리해 답의 공개 단위가 달라짐

- **위치:** `app/app.js:170–180`, `:244–251`, `:592–593`; `app/deck-spec.js:314–358`
- **증상 A:** `[[가**나**다]]`라는 답 하나가 `가`, `나`, `다`의 세 단계로 열린다. 색·밑줄·형광펜 등으로 서식 조각이 나뉘어도 같은 문제가 생긴다.
- **증상 B:** `[[가]][[나]]`처럼 붙어 있는 두 빈칸은 처음에는 두 `.ans`지만, 표기 재생성이나 편집 저장 뒤 `[[가나]]`로 합쳐져 한 단계가 된다. 글자와 서식의 왕복은 맞아도 수업 자료의 공개 단위는 보존되지 않는다.
- **근거 [실행 확인 — 격리]:** 실제 파서·직렬화기·HTML 생성 함수를 VM에서 실행했다. `[[가**나**다]]`는 `.ans` 3개, `[[{{blue:가}}나]]`는 2개를 생성했다. 실제 `setupSteps`에 생성 HTML의 문서 순서를 제공하면 각각 별도 답 단계로 등록됐다. `runsToMarkup(parseMarkup('[[가]][[나]]'))`와 인접 `.ans` 두 개의 실제 `elToMarkup` 결과는 모두 `[[가나]]`였다.
- **원인 [정적 확인]:** `a`가 boolean이어서 어느 `[[...]]`에 속하는지 구분하지 못한다. HTML은 run마다 답 span을 만들고, 단계는 span마다 등록한다. 저장도 `a`가 같은 조각을 합치거나 연속된 `a=true` 사이에 경계를 쓰지 않는다.
- **수정 제안:** 빈칸의 논리적 식별자 또는 구간 경계를 서식 run과 별도로 보존한다. 하나의 빈칸 안에서 서식이 바뀌면 여러 span이어도 한 단계로 묶고, 서로 다른 인접 빈칸은 직렬화·편집 저장 후에도 구분한다.
- **확인 방법:** 한 답 안의 여러 색·굵게·밑줄·형광펜, 인접한 같은 서식 빈칸, 그 답의 일부 서식 변경을 시험한다. 글자·서식뿐 아니라 빈칸 개수와 공개 순서도 왕복 전후 같아야 한다.

### 2. [중간] 숨긴 답이 CSS상 투명할 뿐 접근성용 숨김 상태는 없음

- **위치:** `app/style.css:120–121`, `app/app.js:603–608`
- **증상:** 줄·표 행이 나온 뒤 아직 열지 않은 답도 보조기기에 노출될 수 있다. 시각적으로는 밑줄 빈칸이지만 DOM에는 정답이 그대로 있고, 접근성 숨김 상태가 없다.
- **근거 [정적 확인]:** `.ans.hid`는 글자·바탕을 투명하게 할 뿐이다. 일반 단계의 `visibility:hidden`과 달리 답에는 가시성 숨김을 적용하지 않으며, `showStep`도 `aria-hidden`이나 대체 빈칸 설명을 설정하지 않는다.
- **근거 [실행 확인 — 격리]:** 실제 `setupSteps`·`showStep`를 DOM 대역에서 실행하면 `.hid` 상태의 답에도 `textContent='답'`이 남았다. 접근성 트리 자체를 시험한 것은 아니다.
- **근거 [추정]:** 실제 VoiceOver 등에서 읽히는 구체적인 순서·동작은 이번 검토에서 확인하지 않았다. 다만 색의 투명도에만 의존하는 현재 코드는 보조기기에도 답을 숨긴다는 보장을 제공하지 않는다.
- **수정 제안:** 답의 시각 상태와 함께 `aria-hidden` 등을 갱신하고, 필요하면 별도의 “빈칸” 설명을 제공한다. 답을 열었을 때 읽히도록 복구하며, 단계 안내나 읽기 알림은 과도하게 반복되지 않게 설계한다. 편집·인쇄용 DOM에는 발표용 숨김이 남지 않아야 한다.
- **확인 방법:** 실제 보조기기에서 제목 빈칸과 공개된 줄·행 안의 미공개 답을 확인하고, 다음·이전 조작에 따라 노출 상태가 함께 바뀌는지 본다.

### 3. [낮음] 편집용 빈칸 바탕 스타일이 썸네일·인쇄용 DOM에도 적용됨

- **위치:** `app/style.css:119`; `app/app.js:547`, `:1641–1646`
- **증상:** 편집 모드에서 인쇄하면 편집 화면 안내용 옅은 붉은 바탕이 인쇄용 답에도 적용될 수 있다. 썸네일도 같은 규칙에 포함된다. 편집 모드에서 출력할 때와 발표 모드에서 출력할 때의 스타일 조건이 달라진다.
- **근거 [정적 확인]:** 선택자가 `.edit .slide .ans`여서 `contenteditable`이나 편집 무대에 한정되지 않는다. 썸네일·`printHost`의 슬라이드도 `.slide`이고 같은 `body.edit` 아래에 있다. 인쇄용 `makeSlide`에 `editable:false`를 줘도 이 CSS 조건은 그대로이며 인쇄 CSS에 해당 바탕을 제거하는 규칙도 없다.
- **확인 한계:** 이번에는 Chrome을 실행하지 않았으므로 실제 PDF의 바탕 인쇄 결과를 확인하지 않았다. CSS 적용 범위와 DOM 구조의 불일치를 확인한 것이다.
- **수정 제안:** 편집용 표시는 실제 편집 가능한 칸이나 편집 무대에만 적용하고, 인쇄에서는 바탕을 명시적으로 초기화한다. 썸네일에도 편집 표시를 둘지 정책을 정해 안내와 맞춘다.
- **확인 방법:** 같은 빈칸 덱을 편집·발표 모드에서 각각 인쇄해 비교하고, 썸네일에는 의도한 표시만 남는지 확인한다.

## 추가 확인 결과

### 표기·호환성·안전성

- **[실행 확인 — 격리]** 빈칸 on/off·굵게·밑줄·형광펜 16개 상태, 기본/목록/사용자 색 3개, 일반 글자·표기 기호·줄바꿈·이모지 4개 사례의 192개 조합이 글자·서식 상태 기준 왕복을 통과했다. 중첩 색, `\[`·`\]`, 닫지 않은 빈칸도 별도로 확인했다. 이 검사는 빈칸의 논리적 경계 보존을 뜻하지 않는다(문제 1).
- `.ans` 내부의 HTML 같은 글자는 기존 `esc()`로 이스케이프된다. `[[{{#123456:<img src=x>}}]]`도 실제 태그가 아니라 글자로 렌더링됐다. 기존 색 검증 경로는 그대로다.
- **[실행 확인 — 격리]** 단일 `[한 칸]`은 표시 글자가 유지되며 재저장 시 이스케이프가 추가된다. 반면 기존 `[[배열]]`은 `main`에서는 괄호까지 일반 글자였지만 이제는 `배열`이라는 빈칸 답이다. 기본 `step:page`에서도 괄호가 사라진다. 새 문법에 따른 호환성 변화이며, 기존 덱을 실제로 조사하지는 않았다. 기존 이중 대괄호를 문자 그대로 유지하려면 이스케이프가 필요하다는 안내를 보충하면 좋다. `code`·`num`은 plain 필드여서 그대로다.
- **[실행 확인 — 격리]** `settings.step`의 정상 값 `page`·`line`은 유지하고 누락·null·잘못된 문자열·숫자·상속 속성 이름은 `page`로 돌아갔다. 과거 덱의 기본 넘기기는 장 단위다.
- **[실행 확인 — 격리]** 본문·표에 `정답`과 `[[정답]]`을 넣은 합성 덱의 `check-deck` 결과가 같았다. 자동 정렬과 길이 검사도 공통 `stripMarkup`을 사용하므로 빈칸 표기 기호를 글자 수에 포함하지 않는다.

### 단계 구성·이동·숨긴 개체

- **[실행 확인 — 격리]** 실제 `slideHTML`과 단계 함수를 실행했다. 생성 HTML의 유효한 태그·문서 순서·class·텍스트만 표현하는 간단한 DOM 대역을 제공했으며 브라우저 HTML 파서·레이아웃 엔진은 사용하지 않았다.
- 본문 사례에서 제목 빈칸 → 첫 줄 → 그 줄의 답들 → 둘째 줄 → 그 줄의 답 순서였다. 공백뿐인 줄은 단계에서 빠지고 줄바꿈 자리는 남았다. 줄 기준은 화면 자동 줄바꿈이 아니라 원문의 `\n`이다.
- 단계 형태의 화살표는 다음 상자와 같은 단계로 묶였다. 표는 머리 줄의 빈칸이 먼저 단계에 들어가고 이후 본문 행별 공개와 그 행의 답들이 이어졌다. 제목·머리 줄 자체는 처음부터 보이지만 그 안의 빈칸 답은 별도 단계다. 스킬 문서는 제목에 빈칸을 넣지 않도록 안내한다.
- `layout.hidden`으로 본문 개체를 숨기면 그 안의 줄과 답은 렌더링·단계 목록에서 빠졌다. 그림·스티커는 단계 표시를 붙이지 않아 처음부터 보인다. 스티커의 픽셀 안에 있는 빈칸 글자는 이 텍스트 문법으로 해석할 수 없다.
- 실제 `advance`로 단계 수만큼 앞으로 이동하면 `stepI`가 끝에 도달하고, 다음 입력은 `go(다음 장,false,0)`로 넘어갔다. `setupSteps(...,'end')` 뒤 이전 입력은 마지막 단계부터 숨겼다. `page` 모드에서는 단계 0개이고 `data-unit`도 없었다.
- **[정적 확인]** 장 전환 시 새 `curEl`을 만든 뒤 그 요소 안에서만 단계 목록을 만든다. 이전 슬라이드는 별도 DOM으로 남아도 새 단계 탐색에 포함되지 않는다. 입력은 동기적으로 카운터를 갱신하며 애니메이션 종료 콜백에서 단계 카운터를 다시 바꾸는 코드는 없다. 연속 입력 중 실제 전환 화면과 클릭 위치는 시험하지 않았다.
- **[정적 확인]** 발표 시작은 새 DOM에서 0단계로, 끝내기는 편집 DOM으로 다시 만든다. 창 크기 변경·글꼴 로드 후에는 같은 DOM을 맞추므로 단계 목록을 재생성하지 않는다. 반면 `renderStage`를 다시 호출하는 경로는 `stepAt`을 주지 않으면 공개 상태를 0으로 초기화한다. 발표 중 재생성이 필요한 기능을 추가할 때는 현재 단계 보존 여부를 정해야 한다.
- 넘기기 설정 변경은 저장만 하지만 일반 UI에서는 발표 중 설정 패널이 숨겨지고, 발표 시작 시 설정에 맞춰 재생성한다. 이번 경로에서 별도의 확정 오류를 발견하지 못했다.

### 편집·썸네일·인쇄·숨김 CSS

- **[정적 확인·실행 확인 — 격리]** 기본 렌더링은 `steps` 옵션이 없으므로 줄 단위 wrapper·숨김 class를 만들지 않고 답을 표시한다. 썸네일·인쇄는 이 기본 옵션으로 새 슬라이드를 만들며 `setupSteps`를 호출하지 않는다. 발표 DOM의 단계 숨김을 그대로 복사하는 방식이 아니다. 편집 바탕 CSS의 범위는 문제 3에 해당한다.
- 색·형광펜·밑줄이 있는 답에도 `.ans.hid`와 하위 요소의 `color`·`background:transparent !important`가 적용돼 기존 사용자 색과 바탕을 덮는다. 밑줄 장식의 실제 외양, 선택 상태의 표시, 대비는 이번에 확인하지 않았다. 보조기기용 숨김은 별개다(문제 2).
- 클릭은 기존처럼 화면 왼쪽 30%는 이전, 나머지는 다음이며, 빈칸을 직접 골라 여는 방식은 아니다. 키보드의 다음·이전 입력도 같은 `advance`를 호출한다.
- 미리 보기 스크립트는 `#s=…&view&all`로 열어 모든 단계를 보이도록 바뀌었다. 초기화 끝의 `setupSteps(curEl,'end')`와 일치한다. 스크립트를 실행하거나 Chrome 대용 실행파일로 우회 시험하지 않았다.

### 문서·회귀·검토 한계

- 두 스킬 문서는 바이트 단위로 같고, 수업 자료·빈칸·넘기기 설정 안내가 추가돼 있다. 문서의 “빈칸 하나씩” 동작을 지키려면 문제 1의 경계 보존이 필요하다. 제목·그림의 초기 표시와 `page` 기본값 등은 구현과 맞는다.
- **[실행 확인 — 격리]** 기본 13장의 생성 `slideHTML` 문자열은 `main`과 전부 같았다. `app.js`, `deck-spec.js`, `preview-deck.mjs`의 `node --check`와 `git diff --check`도 통과했다. 버전은 `1.12.0`이다.
- 검사 스크립트용 합성 덱은 운영체제 임시 폴더에 만들고 종료 시 제거했다. 사용자 덱·생성기록은 읽거나 바꿀 필요가 없었다. 요청서의 Chrome 캡처·실제 편집·단계 동작 결과는 선행 작업자의 보고이며 이번에 재검증한 결과가 아니다.

## 의견 (우선순위 순서)

1. **빈칸 경계를 서식 조각과 분리한다(문제 1).** 저장·편집 전후의 빈칸 개수와 공개 단위까지 시험한다.
2. **답의 접근성 상태를 시각 상태와 함께 관리한다(문제 2).** 실제 화면 읽기 확인이 필요하다.
3. **편집용 표시의 CSS 범위를 줄이고 출력에서 초기화한다(문제 3).** 이후 기존 이중 대괄호의 문자 표기 방법도 안내한다.

이 문서는 검토와 수정 제안만 담았다. 소스 수정·커밋·Chrome 실행·텔레그램 등 외부 전송은 하지 않았다.
